# csvsift · 2026-10-25

## 一、我拆的是哪个项目

**[wireservice/csvkit](https://github.com/wireservice/csvkit)** · 6,418 星 · MIT · Python

一句话定位：把 CSV 当成 Unix 管道里的一等公民——`csvcut` 切列、`csvgrep` 筛行、`csvsort` 排序、`csvjoin` 连接、`csvstat` 统计，十四个命令各干一件事，串起来用。

**为什么选它。**

第一条理由很实在：它被投诉的地方，正好是我每天在做的事。我要的东西从来都很朴素——从一张 CSV 里挑几列、按某个条件筛掉几行、按金额排个序、看看每列都有什么。csvkit 能做这些，但它做这些的时候会**顺手改我的数据**。

第二条：它的问题不是「功能不够」，而是「功能太多、抽象太重」。十四个命令共享一套参数解析器，却没有人能加一个 `--limit`；一个 2012 年提的类型推断开关，到今天还是 open。这种「活得太久、长得太胖」的项目，正是最适合砍一刀的对象。

第三条是可行性：核心逻辑（选列、筛行、排序、统计）不依赖任何外部服务，纯文本进纯文本出，能在一天里做到「比原版简单且真的能跑」。

## 二、它怎么做的

### 骨架

```
                     ┌──────────────────────────┐
                     │  CSVKitUtility (cli.py)   │  ← 630 行，所有命令的父类
                     │  · 通用参数 (-d -e -t -n) │
                     │  · 输入打开 (gz/bz2/xz/…) │
                     │  · 列标识符解析            │
                     └────────────┬─────────────┘
                                  │ 继承
        ┌────────────┬────────────┼────────────┬────────────┐
     csvcut       csvgrep      csvsort      csvstat      csvsql
      (69 行)      (…)          (…)         (393 行)     (…)
        │            │            │            │            │
        └────────────┴────────────┴────────────┴────────────┘
                                  │
                        ┌─────────▼──────────┐
                        │   agate.Table      │  ← 全量物化，类型推断在这里
                        │   Column / DataType│
                        └─────────┬──────────┘
                                  │
                        ┌─────────▼──────────┐
                        │  csv / json / text │
                        └────────────────────┘
```

### 核心链路，四步

**第一步，把文件读成行。** `CSVKitUtility.get_rows_and_column_names_and_column_ids()` 做三件事：跳过 `--skip-lines`、取第一行当表头（或者 `--no-header-row` 时造 `a,b,c…`）、把 `-c` 里的标识符翻译成列下标。这一步是**流式**的——它返回的是 `csv.reader`，还没读进内存。

**第二步，决定要不要变成 Table。** 这就是分水岭。`csvcut` 拿到 reader 就直接开始写输出，内存恒定；`csvstat`、`csvsort`、`csvlook`、`csvjoin`、`csvsql` 则调用 `agate.Table.from_csv()`，把整个文件变成一张表。

**第三步，类型推断。** `agate.TypeTester` 是一条链：

```
Boolean → Date → DateTime → TimeDelta → Number → Text
```

它对**整列**依次试：这一列所有值都能被 `Boolean` 解析吗？不能就试 `Date`，再不能试 `Number`……第一个全列通过的类型胜出。`Number` 用 `Decimal` 解析，`Date` / `DateTime` 用 `dateutil`，`TimeDelta` 用 `pytimeparse`，所以 `2026-09-02` 会先被 `Date` 抢走，`012345` 会被 `Number` 抢走。

**第四步，输出。** 每个命令自己写自己的输出格式：`csvlook` 画表格、`csvjson` 出 JSON、`csvformat` 改分隔符。格式逻辑散在十四个文件里，没有共用层。

### 三个关键设计决策

1. **`csvsql` 不发明查询语言，直接把表塞进 SQLite。** 用户已经会 SQL，何必再学一套。代价是必须全量物化。
2. **类型链是可插拔的类，不是硬编码的 if。** 想支持新类型，加一个类注册进去。这个抽象本身没问题。
3. **流式/缓冲的边界写在文档里。** `docs/contributing.rst` 有一节 "Streaming versus buffering"，明确列出哪七个命令会吃内存。作者知道代价在哪，选择把它公开而不是藏起来。

### 一句话总结它的架构

**「一层薄薄的命令 + 一层厚厚的类型系统」。** 薄的那层很 Unix，厚的那层很 ORM。所有痛苦都来自厚的那层：它假设自己是数据库，可用户只是想在命令行里看一眼数据。

## 三、它哪里让人难受

### 1. 类型推断会静默改写数据（issue #1246）

这是最要命的一条。原文：

> "The underscores in the ID field are getting dropped. I've tracked this down to type inference. Running `csvjoin` with the `--no-inference` option produces the desired behaviour."
>
> "I was a bit surprised by this, as it seems a bit aggressive of a default inference on what I believe to be a very common text pattern."

维护者的回复解释了机制，但没否认结果：

> "We use Python's `Decimal` for parsing... `Decimal('1_1')` → `Decimal('11')`. Decimal works this way because, in Python, the underscore can be used as a grouping character."

也就是说：Python 允许 `1_000_000`，于是 `100_1` 被当成了数字一零零一。我在本机装了个 csvkit 复现，一字不差：

```
$ csvjoin -c Name f1.csv f2.csv
Name,Type,ID
MHYS,foo,1001        ← 原值 100_1
JABI,bar,103011     ← 原值 1030_11
```

**为什么这是个真问题：** 它不报错、不警告、不留痕。你的 ID 在管道中间被改了一位，而你看到的结果长得完全正常。用户的原话最准确——"the root cause of surprise was that csvkit was doing any datatype inference at all"。他以为自己在切列连接，工具却在替他理解数据类型。

### 2. 类型推断不能按列关掉（issue #151）

2012 年 3 月开的，14 条评论，到今天还是 open。标题就是需求：

> "Allow disabling/forcing type inference for certain columns only"

正文只有草稿级别的两行："A mapping? `--types int,varchar`. A .csvt?"

`--no-inference` 是**全表**开关。可现实是：一张表里 `amount` 想当数字，`zip` 想当字符串。全表关掉，`csvstat` 退化成字符串统计；全表打开，邮编变整数。用户被逼在两个错误之间二选一。

**为什么这是个真问题：** 类型是**列**的属性，不是**表**的属性。把粒度搞错一层，开关就永远不够用。

### 3. 报错不告诉你怎么办（issue #1251）

> "This is a strange CSV file, but it does seem to have a header line and three columns. `csvjson` seems to be having trouble with the data columns."

实际抛的是：`ValueError: Row 0 has 45 values, but Table only has 3 columns.`

45 个值怎么来的、哪一行、是引号没闭合还是分隔符猜错——一个字都没有。用户只能自己去猜。

### 4. 十四个命令，没有一个能「取前 10 行」（issue #669）

2016 年开的：

> "Hey I have a large CSV I'm looking to break up into smaller chunks to perform an import. Is this functionality already available with `csvcut` or `csvgrep`. I was reviewing the docs but I didn't see any avenue to do it?"

要分批导入，第一步就是取前 1000 行。csvkit 做不到。绕法是 `csvcut -c 1 f.csv | head -1000`，但这样没法先按行号偏移再切列，而且 `head` 会触发 BrokenPipe（项目里为此专门装了 SIGPIPE 处理器——说明这个坑大家都踩过）。

**为什么这是个真问题：** 十四个命令共享同一套参数解析器，加一个 `--limit` 的成本极低。它不在，不是因为难，是因为没人把它当成核心需求。

### 5. 大文件直接放弃（issue #737）

维护者自己写的：

> "For files larger than 1GB, I don't think we can expect csvkit to ever perform well, so we can at least start there."

根因还是第二步那个分水岭：`agate.Table` 是全量物化的，每个值都变成 Python 对象。54 MB 的 CSV 展开成对象图，内存要翻好几倍。

### 6. 表头规范化提了十一年（issue #396）

> "This is specifically with regards to `csvsql`, where loading a CSV file with `Some manually entered - header (TM)` will give you a data structure that is really hard to query."

提出者自己去读了代码，结论是 "would require pulling the option through many intermediate functions"。一个字符串处理需求，被架构逼成了跨层改造。

### 7. BOM 会跟着列名一起进来（实测）

```
$ csvstat orders.csv
  1. "﻿order_id"
```

那个 `﻿` 是 UTF-8 BOM。默认编码是 `utf-8` 不是 `utf-8-sig`，于是第一列的名字永远带一个看不见的字符。你写 `csvcut -c order_id` 会报「没有这一列」，而屏幕上看起来一模一样。

**为什么这是个真问题：** 这是 Excel 导出的 CSV 的默认状态。也就是说，它发生在几乎每一个真实场景里。

## 四、我们做了什么

**一句话定位：一个命令，五个动词，值永远是你文件里的原始文本。**

```
csvsift [文件] [-c 列] [-w 条件] [-s 排序] [-n 条数] [-g 分组 --agg 聚合] [--stats] [-f 格式]
```

### 砍了什么、留了什么、加了什么

| 类别 | 内容 | 为什么 |
|------|------|--------|
| **砍掉** | `csvjoin` `csvstack` `csvsql` `sql2csv` `csvpy` `in2csv` | 多表连接、格式转换、交互式 shell 是三类不同需求。塞进来会让参数表翻倍，而日常 90% 的用法是看一张表。 |
| **砍掉** | agate 依赖链 | 类型推断、`Table` 物化、`Decimal` 解析下划线，全在这一层。 |
| **砍掉** | 类型推断本身 | 类型只在比较和排序的瞬间决定，从不写回数据。 |
| **保留** | 列引用语法 `1,id,3-5` | csvkit 最好用的设计，直接照抄交互（不是代码）。 |
| **保留** | `--names` | 每天用十次的功能。 |
| **合并** | 十四个命令 → 一个命令 + 六个参数 | `-c/-w/-s/-n/-g/--stats` 都是同一张表的修饰，天然应该写在一行里。 |
| **新增** | `-n/--limit`、`--offset` | 补 #669。 |
| **新增** | 每列独立升降序 `-s city,-amount` | 补 #931。 |
| **新增** | 表头宽松匹配（大小写 / slug） | `Some manually entered - header (TM)` 直接写 `-c some_manually_entered_header_tm`，绕开 #396 而不用改数据。 |
| **新增** | 参差行可读警告 | `some rows have more fields than the header; extra values were dropped (first at line 2)`，而不是 `Row 0 has 45 values` |
| **新增** | BOM 默认剥掉 | 默认编码 `utf-8-sig`。 |

### 核心算法怎么工作

只有一条规则，但它决定了整个工具的性格：

> **一个值是不是数字，在「比较的那一刻」决定，而且判错了也不会改数据。**

判断用的正则写得很死：

```
^[+-]?(?:\d+(?:\.\d*)?|\.\d+)(?:[eE][+-]?\d+)?$
```

再加一条：**前导零不算数字**。`012345` 不是 12345，是邮编。

举三个例子：

| 输入 | csvkit | csvsift | 为什么 |
|------|--------|---------|--------|
| `100_1` | `1001` | `100_1` | 下划线不是千位分隔符，是 ID 的一部分 |
| `012345` | `12345`（csvstat 报 Number，均值 276,116.25） | `012345`（报 text，不给均值） | 前导零意味着「这是一个编号」 |
| `9` vs `10` | `10 > 9` | `10 > 9` | 两边都是数字，按数字比 |

**排序是另一条规则，也是这次最值得讲的一处。** 一开始我让每个值各自决定排序带（空 → 数字 → 文本），结果邮编列排出来是：

```
200120
000001
012345
```

因为 `200120` 被归进了「数字带」，而 `000001` 被归进了「文本带」，数字带整体排在文本带前面。**同一个问题换了个形状又回来了。**

修法是：**一列只用一种排法。** 先扫一遍整列，全是合法数字就按数字排，否则整列按文本排。`012345` 一旦出现，整列都按文本排，于是：

```
000001
012345
200120
```

代价是「一列里混着 `9`、`10`、`abc`」时，`10` 会排在 `9` 前面。这是有意的：**一列一个排法，是可预测的；一列两个排法，是不可预测的。** 而且这个决定是可见的——`--stats` 的 `type` 列会告诉你这一列被当成了什么。

## 五、和原版差在哪

| 维度 | csvkit | csvsift |
|------|--------|---------|
| 命令数 | 14 个可执行文件 | 1 个命令 + 6 个参数 |
| 依赖 | agate / agate-dbf / agate-excel / agate-sql / python-dateutil / parsedatetime / pytimeparse / leather… | 无（纯标准库） |
| 代码量 | 47 个 .py，约 26 万字节 | 1 个 .py，1,480 行 |
| 值类型 | 推断后**写回** Python 对象 | 永远是原始文本，只在比较时临时解析 |
| `100_1` | `1001` | `100_1` |
| `012345` | `12345`（csvstat 报 Number，均值 276,116.25） | `012345`（报 text，不给均值） |
| 排序方向 | 整条命令同向 | 每列独立升降序 |
| 取前 N 行 | 没有 | `-n N` / `--offset N` |
| 表头带空格和符号 | 得先改名 | 大小写 + slug 宽松匹配 |
| 参差行 | `Row 0 has 45 values, but Table only has 3 columns` | 补齐/截断 + 说明第几行 |
| BOM | 默认不处理（列名带 `\ufeff`） | 默认剥掉 |
| 输出格式 | `csvlook` / `csvjson` / `csvformat` 三个命令 | 一个 `-f csv\|tsv\|json\|ndjson\|table\|md` |
| 多表连接 / Excel / SQL | 有 | 明确不做 |
| 统计 20 万行 | 219.13 秒 / 47.2 MB | 9.89 秒 / 42.9 MB |
| 排序 20 万行 | 191.41 秒 / 11.0 MB | 5.32 秒 / 144.2 MB |
| 切列 20 万行 | 4.57 秒 / 10.9 MB | 2.78 秒 / 28.9 MB |

测法：同一份 10.8 MB / 20 万行的 CSV（7 列，含中文城市名、前导零邮编、两位小数金额），csvkit 2.x 装在独立 venv 里，`csvsift` 用系统 Python 3.13。计时用 `time.perf_counter()` 包住整个子进程，内存用 `psutil` 每 5 毫秒采一次 RSS 取峰值。输出全部丢进 `/dev/null`，排除磁盘写入的干扰。

**速度这一栏是压倒性的，但内存这一栏我们输了一项，得说清楚。**

`csvstat` 219 秒，不是笔误。agate 要先把整张表物化，再对每一列跑一遍类型链（`Boolean → Date → DateTime → TimeDelta → Number → Text`），每个类型都要尝试解析全列。20 万行 × 7 列 = 140 万次解析尝试，最后大部分都失败。**它的时间花在「猜」上，而 csvsift 压根不猜。**

排序那一栏，csvkit 只用了 11 MB 内存——因为它把排序溢出到了临时文件（维护者在 issue #737 里提到过 `csvsort` 有过一次性能重写）。我们用 144 MB，因为整张表就在内存里。这是有意的取舍：**用内存换 36 倍速度**，代价写在 README 的「What it does not do」里，不藏。

1M 行 / 54.1 MB 时，csvsift 的四个操作是：统计 40.48 秒 / 43.0 MB，排序 25.90 秒 / 615.8 MB，切列 10.98 秒 / 29.0 MB，筛行 9.99 秒 / 29.7 MB。统计的内存和 20 万行时几乎一样（42.9 → 43.0 MB），因为 distinct 计数到 65,536 就停手了；排序的内存随行数线性涨，这是这条路线的天花板。同一份 1M 行的文件，`csvstat` 跑了 14 分 40 秒还没结束，我手动终止了。

## 六、怎么用

一个文件，零安装。把它放到任何地方，`python csvsift.py` 就能跑：

```bash
python csvsift.py orders.csv                        # 原样打印
python csvsift.py - < orders.csv                    # 读标准输入
```

### 先看有什么列

```bash
$ python csvsift.py examples/orders.csv --names
1: order_id
2: city
3: product
4: qty
5: amount
6: zip
7: placed_at
```

### 切列 + 筛行 + 排序 + 截断，一行搞定

```bash
$ python csvsift.py examples/orders.csv -c city,amount --where "amount > 1000" -s=-amount -n 3
city,amount
杭州,4999.00
上海,2499.50
深圳,1947.00
```

`-c` 选列、`-w` 筛行、`-s=-amount` 按金额降序（`-` 前缀）、`-n 3` 只出三行。注意 `-c` 只影响**打印**：`--where` 和 `-s` 永远看文件的原始列，所以你可以按没打印出来的列筛。

### 分组统计

```bash
$ python csvsift.py examples/orders.csv -g city --agg "count(*), sum(amount), avg(amount)"
city  count(*)  sum(amount)  avg(amount)
----  --------  -----------  -----------
北京         3         1759  586.3333333
上海         3       4694.5  1564.833333
深圳         2         2596         1298
广州         2          689        344.5
杭州         2       5058.6       2529.3
```

`--agg` 支持 `count(*)`、`count(col)`、`sum`、`avg`、`min`、`max`、`distinct`、`median`，参数可以是表达式（`sum(amount * qty)` 也行）。

### 这一列到底是什么

```bash
$ python csvsift.py examples/orders.csv --stats
column     type    filled  empty  unique  min         max                mean
---------  ------  ------  -----  ------  ----------  ----------  -----------
order_id   text        12      0      12  A-1001      A-1012
city       text        12      0       5  上海        深圳
product    text        12      0       5  USB-C 线    鼠标垫
qty        number      12      0       6  1           10          3.333333333
amount     number      12      0      11  59.60       4999.00     1233.091667
zip        text        12      0       5  012345      518000
placed_at  text        12      0       9  2026-09-02  2026-09-10
```

`zip` 是 `text`，因为 `012345` 不是数字——所以整列按文本排，也不给均值。`type` 是**报出来的**，不是改出来的。

### 原始值不会被改

```bash
$ python csvsift.py examples/ids.csv
Name,Type,ID
MHYS,foo,100_1
JABI,bar,1030_11
```

同一份数据，`csvjoin` 会输出 `1001` 和 `103011`。想要 JSON 里的数字类型，得自己开口：

```bash
$ python csvsift.py examples/orders.csv -c zip,amount -n 2 -f json --numbers
[{"zip": "012345", "amount": 1298},{"zip": 200120, "amount": 2499.5}]
```

注意 `200120` 变成了数字，`012345` 还是字符串——前导零在 `--numbers` 里同样不认。

### 报错说人话

```bash
$ python csvsift.py examples/orders.csv -c amout
csvsift: no column named 'amout'.
  did you mean: 'amount'
```

字段数对不上的行，不会让整个命令崩掉，但也不会被悄悄吞掉：

```bash
$ printf 'a,b\n1,2,3\n4\n' | python csvsift.py -
csvsift: some rows have more fields than the header; extra values were dropped (first at line 2)
csvsift: some rows have fewer fields than the header; missing values were filled with empty strings (first at line 3)
a,b
1,2
4,
```

### 输出格式随你

```bash
python csvsift.py f.csv -f table      # 给人看的对齐表格（中文字符按两格算）
python csvsift.py f.csv -f md         # Markdown 表格，粘进文档
python csvsift.py f.csv -f json       # JSON 数组
python csvsift.py f.csv -f ndjson     # 一行一条，适合喂管道
python csvsift.py f.csv -f tsv        # 制表符
```

### 跑测试

```bash
$ python -m unittest discover -s tests
Ran 195 tests in 0.86s
OK
```

## 七、开发中踩的坑

**坑一：为了嗅探分隔符，把整个文件吃掉了。**

`Table` 初始化时要先读一段样本判断分隔符（`,` / `;` / `\t` / `|`）。我读了 64KB，然后把「剩下的部分」交给 `csv.reader`——结果小于 64KB 的文件，样本读完流就空了，程序报 `the input is empty`。

修法是把样本切成两半：`head`（最后一个换行之前的完整行）和 `tail`（半行），`tail` 要跟流里读到的第一行**粘回去**，否则一行会被切成两行，字段数全乱。

回归测试：`test_no_trailing_newline`（文件末尾没换行）、`test_large_file_crosses_sample_boundary`（两万行，必然跨过 64KB 边界）、`test_empty_input`。

**坑二：排序的「分带」把邮编排乱了。**

上面第四节讲过。`test_postcodes_sort_as_text` 抓到的，第一版输出是 `200120, 000001, 012345`。改成整列统一排法。

**坑三：`abs()` 直接对字符串调用。**

`abs(amount)` 里我写的是 `abs(args[0](row))`，但 `amount` 求值出来是字符串 `"-5"`，于是 `TypeError: bad operand type for abs(): 'str'`。必须先 `as_number()` 再取绝对值。回归测试：`test_function_abs`。

**坑四：JSON 里空单元格变成了 `""` 而不是 `null`。**

行里的空值是 `""`（字符串），不是 `None`。`json_value()` 只判了 `None`，于是 JSON 输出 `{"a": ""}`。改成先过一层 `cell()` 归一化。回归测试：`test_json_empty_cell_is_null`。

**坑五：`-s -amount` 被 argparse 当成了选项。**

`csvsift f.csv -s -amount` 会报 `expected one argument`——argparse 认为 `-amount` 是一个新选项。这不算 bug，但很容易踩。加了个 `:desc` 后缀作为等价写法：`-s amount:desc`，同时文档里统一写 `-s=-amount`。回归测试：`test_sort_descending`、`test_parse_sort_spec`。

**坑六：`--stats` 里 zip 列的 min/max/mean 全是错的。**

第一版里 zip 被正确识别成 `text`，但 min/max 用的是「分带」比较，于是 min 显示 `200120`、max 显示 `012345`（文本带在数字带后面），还顺手算出了一个均值 `364040`——把一个邮编列的平均值算出来了。

修法：类型判成 `text` 就用字典序取 min/max，并且**不出均值**。回归测试：`test_text_min_max_are_lexicographic`、`test_mean_only_for_numbers`。

**坑七：我自己的测试写错了两个。**

`test_endswith_operator` 里我写 `"alpha".endswith("ta")` 断言为 True——`alpha` 结尾是 `ha`，不是 `ta`。测试红了，第一反应是代码有 bug，查了才发现是断言写错。另一处是 `-s -amount` 那个用法本身就跑不通（见坑五）。**测试红的时候，先怀疑测试。**

## 八、一句话总结

**csvkit 花了十四年把 CSV 变成一个数据库，而我只想看一眼数据——所以 csvsift 只做一件事：把值原样还给你，需要比较的时候才临时当它是数字。**
