# mddeck · 2026-10-27

## 一、我拆的是哪个项目

[marp-team/marp-cli](https://github.com/marp-team/marp-cli)

- **星标**：3,891
- **许可证**：MIT
- **语言**：TypeScript
- **一句话定位**：把 Marp 风格的 Markdown 转成 HTML、PDF、PPTX 和图片，一套 Markdown 走完所有演示场景。
- **活跃度**：最近一次提交 2026-09-08，仍在维护。

为什么选它？因为它的痛点是**结构性**的，不是 bug。为了把 DOM 画成 PDF，它必须拉起一个真实的 Chrome；
一旦这个前提成立，"每次转换留一个 18MB 临时目录""找不到浏览器就用不了""内容溢出了没人告诉你"
这三件事就全都变成了必然结果。一个 3,900 星的项目被一个架构决定绑住手脚，这种题最值得拆。

顺带说一句：今天 GitHub Trending 上清一色是 agent / skill 类仓库，没有可拆的核心算法，
所以选题走的是搜索接口 + 候选对比（marp-cli / pre-commit / ajv / hyperfine），
按"痛点是否有原文证据 + 能否在一天内做出有价值的精简版"筛下来，marp-cli 最合适。

## 二、它怎么做的

一句话概括：**Markdown 先被 Marpit 变成一页页固定尺寸的 HTML，然后交给浏览器去画。**

```
slides.md
   │
   ├─ src/marp-cli.ts ──► src/config.ts（cosmiconfig 读 .marprc / package.json / marp.config.js）
   │
   ├─ src/engine.ts ──► Marpit / Marp Core（Markdown → 每页一个 <section>）
   │        │
   │        └─ engine/ 插件：directive（指令）、meta（页面元信息）、
   │                        info（版本水印）、pdf/outline（书签）、transition（过渡）
   │
   ├─ src/templates/ ──► 套模板：bespoke（20 个运行时模块）/ bare
   │
   └─ src/converter.ts ──► 按输出类型分叉
            ├─ html  → 模板 + jsdom 后处理，写文件        ← 不需要浏览器
            ├─ pdf   → Puppeteer 打印                      ← 需要 Chrome
            ├─ png   → Puppeteer 截图                      ← 需要 Chrome
            └─ pptx  → 截图后塞进 PPTX 当背景图             ← 需要 Chrome（可编辑模式还要 LibreOffice）
```

源码规模：`src/` 下 76 个 TS 文件、8,413 行；`test/` 下 42 个文件、10,935 行。测试比源码还多，
说明团队很认真。8 个运行时依赖，83 个开发依赖。

几个关键设计：

**固定画布。** 每页就是一个 1280×720 的 `<section>`，内容往里灌。主题只写一套 CSS，
预览、PDF、图片三种输出共用同一份 DOM——因为它们画的是同一个东西。这个抽象很漂亮，
也是主题生态能成立的原因。

**浏览器当渲染器。** PDF 不是自己画的，是让 Chrome 打印页面；PNG 不是自己渲染的，
是让 Chrome 截图。这招省掉了整个排版引擎，但代价是每次转换都要一个浏览器实例，
而浏览器实例要一个 user-data-dir（`src/utils/tmp.ts` 用 `tmp` 包生成临时目录）。

**浏览器得自己找。** `src/browser/finders/` 下有 chrome / edge / firefox 三套路径嗅探，
还要处理 macOS 的 .app bundle 校验、WSL 路径转换、snapd 装在沙箱里读不到 `/tmp` 的特例。
README 第 47 行把这件事写成硬前置条件："你必须在本地装一个 Google Chrome、Microsoft Edge 或 Mozilla Firefox"。

## 三、它哪里让人难受

### 十天 400GB

> "On Windows 11 systems, marp-cli creates numerous temporary folders (named "marp-cli-xxxxx" with random suffixes)
> in the user's Temp directory. Each folder occupies approximately 18MB of disk space. ... After just 10 days of
> operation, these temporary files have accumulated to over 400GB on my C: drive"
>
> —— [#678](https://github.com/marp-team/marp-cli/issues/678)，8 条评论，仍然 open

这不是泄漏，是架构。每跑一次 `marp`，就启动一个 Chrome，Chrome 启动就要一个干净的 profile 目录，
profile 里有一堆默认资源。用户批量跑 10 天，硬盘上就多了 400GB 的 Chrome 空壳。

为什么这是个问题？因为对一个"把 Markdown 转成 PDF"的需求来说，磁盘上多出 400GB 是完全不成比例的代价。
用户甚至没法自己清——他不知道哪些目录能删。

### 装了 Chromium 也找不到

> ```
> [  INFO ] [Preview] Opening file:///tmp/presentation.html...
> [ ERROR ] You have to install Google Chrome, Chromium, or Microsoft Edge to convert slide deck with current options.
> ```
>
> —— [#475](https://github.com/marp-team/marp-cli/issues/475)，用户已经 `brew install chromium`

这个报错的荒谬之处在于：用户明明装了，工具说没装。原因是它按固定路径找，
而 homebrew / snap / 各种发行版把浏览器放在不同地方。为了修这一类问题，
项目里专门有一套 finder 体系——**一个"转 PDF"的工具，有四分之一的基础设施在找浏览器。**

### 内容超出画布，它一声不响

> "When I was previewing, I found that not all the content in markdown was displayed on the page.
> When I converted it to pdf and downloaded it to my local device, I found that the pdf was also not fully displayed.
> May I ask if there are any methods to adaptively display the content on the page?"
>
> —— [#653](https://github.com/marp-team/marp-cli/issues/653)

这一条最要命。固定画布意味着内容多了就会被裁掉，但工具不会警告你。
你写完 30 页，导出 PDF，发到群里，开会时投影出来，第 17 页的最后三行不见了。

为什么它不做检测？因为"内容有多高"只有浏览器知道，而它不想为了这个再开一次浏览器。
一个为了省排版引擎而依赖浏览器的架构，反过来让它没法在构建时回答"这页放得下吗"。

### 输出路径靠猜

> "The `--output` should be relative to the current/working directory so I expect the file `index.html` to go to
> `$PWD/index.html`. ... But here what the help message says: `docs/slides.md => index.html/slides.html`"
>
> —— [#490](https://github.com/marp-team/marp-cli/issues/490)

`-o` 在单文件模式是文件名，在 `--input-dir` 模式是目录。混用时它会造出一个叫 `index.html` 的目录，
再往里放 `slides.html`。用户的反应是"Unpredictable"。

### 参数不成体系

> "some formats are represented as top-level flags, some formats are represented as arguments to generic flags,
> single/multi-page semantics are embedded into the command structure itself"
>
> —— [#723](https://github.com/marp-team/marp-cli/issues/723)

`--html` / `--pdf` / `--pptx` 是开关，`--image png` / `--images png` 是带参开关。
写 CI 循环批量出多种格式时，得为图片单独开一个分支。这是功能一件件加出来的痕迹。

## 四、我们做了什么

**mddeck：Markdown 进，一个自包含 HTML 出。不启动浏览器，但把每一页的排版算清楚。**

这个定位的关键在于把因果关系倒过来。原版因为要用浏览器排版，所以没法在构建时知道内容有多高；
我们不用浏览器，那就自己量——量准了，溢出就成了一个**构建期可回答的问题**，
而不再是一个"投影时才发现"的事故。

### 砍了什么、留了什么、加了什么

| 类别 | 内容 | 理由 |
|------|------|------|
| 砍 | PDF / PNG / PPTX 输出 | 三个都要浏览器，PPTX 的"可编辑"模式还要 LibreOffice。砍掉它们，`src/browser/`、`src/soffice/`、`tmp.ts` 整块消失。要 PDF 就用浏览器打印，`@media print` 已经写好，一页一张 |
| 砍 | 预览服务器 + 文件监听 | 100 页只要 53ms，重新跑一次比守护进程便宜 |
| 砍 | 主题包 / 配置文件体系 | 不读 `.marprc`、不读 `package.json`。配色是两套常量，元信息写在 Markdown 开头几行 |
| 砍 | 演讲者视图 / 过渡 / 分步动画 | bespoke 那 20 个模块是项目里最重的一块，演示现场基本用不到 |
| 留 | `---` 分页 | 这是这个工具存在的理由，必须一模一样 |
| 留 | 1280×720 固定画布 | 固定画布才有可预测的排版，也才能提前算高度 |
| 留 | 键盘导航 / 全屏 / 进度条 / 页码 | 演示的最小可用集 |
| 加 | 构建时高度测量 | 和原版真正的分野：不启动浏览器也知道放不放得下 |
| 加 | 自动缩字号（下限 0.58×） | 溢出的常见解法就是"字小一点"，让人手动改 CSS 是把问题推回给用户 |
| 加 | 溢出报告 + `--check` | 让 CI 能拦住"这页塞太多了" |
| 加 | 直接读图片文件头拿宽高 | PNG/JPEG/GIF/WebP/SVG 的尺寸在头 64 字节里，不需要解码整张图 |

### 核心算法怎么工作

一页的高度 = 每个块的高度之和 + 块之间折叠后的边距。块高度 = 折行数 × 行高。

难点在折行数。没有浏览器，就没有 `measureText`，只能用字符级模型估宽度：

- 中文、全角标点、emoji → 1.0 个字宽
- `i l j t f r I . , ; : ! ' |` → 0.29
- `m w M W @ %` → 0.86
- 大写 0.66，小写 0.53，数字 0.56，空格 0.26

拿一段真实文字算：`"用 Markdown 做幻灯片"` 在 57.4px 下，中文 5 个字符占 5.0em，
`Markdown` 8 个字母占 4.24em，两个空格 0.52em，总共约 9.76em ≈ 560px，可用宽度 1136px，一行放得下。

折行之后是累加。所有间距都以 `em` 表示——`h2` 上边距 0.62em、段落间距 0.62em、列表项间距 0.20em——
这样字号缩到 `s` 倍时，行高和间距同比例缩小。

但**折行数不是线性的**。字号小了，一行能塞更多字，行数掉得比 `s` 快。所以一次算不准，得迭代：

```
scale = 1.0
while measure(blocks, 28 * scale) > available / 1.02:
    scale *= available / measure(blocks, 28 * scale)
# 缩过头了就往回长，每次 1.05 倍，放得下就保留
```

具体例子：`examples/crowded.md` 第 2 页，标题 + 一句说明 + 22 行代码块。
28px 下需要 900 多像素，可用 558px。第一轮算出 `558/900 ≈ 0.62` 倍；
用 0.62 倍重新折行，需要 547px，放得下，定在 16.7px。
最后在 Chromium 里实测这一页 549.1px，和预测的 547.1px 差 0.4%。

### 校准：模型准不准，拿真浏览器验

预测得对，不能靠感觉。做法是：把产出的 HTML 用 Chrome headless 打开，
逐页读 `.body` 的 `getBoundingClientRect().height`，和预测值比。

| 样本 | 页数 | 中位误差 | 最大误差 | 缩放后实际溢出 |
|------|------|----------|----------|----------------|
| `examples/demo.md` | 7 | 0.9% | 1.8% | 0 页 |
| `examples/crowded.md` | 5 | 0.4% | 2.2% | 0 页 |

第一版校准出来是**低估**的，中位误差 6.9%、最大 19.8%。差在哪？三处，全是 CSS 和测量没对上：

1. 段落没写 `line-height`，浏览器用 `normal`（约 1.32），我按 1.55 算——但更关键的是
2. `.body` 是 flex item，形成了 BFC，**最后一个子元素的 `margin-bottom` 不会溢出到外面**，
   所以我"减掉末尾边距"的算法是错的
3. 表格在 CSS 里是 `width:100%`，列宽会被拉满，我却按自然宽度算折行，把某些单元格算成了两行

三处修完，误差从 6.9% 掉到 0.9%。这一步没有捷径——**先假设模型对，再用真实数据打脸，再修。**

因为模型整体仍略微低估，排版时按 `available / 1.02` 收，留 2% 余量。
这个余量是必要的：预测 557px 的页面，在浏览器里可能是 566px，正好切掉一行。

## 五、和原版差在哪

| 维度 | marp-cli | mddeck |
|------|----------|--------|
| 运行时 | Node.js 18+ | Python 3.9+ |
| 依赖 | 8 个运行时依赖（含 puppeteer-core）+ 83 个开发依赖 | 0 |
| 产出 | HTML / PDF / PNG / JPEG / PPTX | 单个 HTML |
| PDF 怎么做 | 拉起 Chrome 打印 | 浏览器 Ctrl+P，`@media print` 已就位 |
| 溢出检测 | 无 | 构建时逐页测量，报告差多少像素 |
| 溢出处理 | 用户自己改 CSS | 自动缩字号，下限 0.58× |
| CI 拦截 | 无 | `--check`，有溢出退出码 1 |
| 配置 | `.marprc` / `package.json` / `marp.config.js` / CLI 参数 | 元信息写在 Markdown 里，0 个必填项 |
| 源码规模 | 76 个 TS 文件 / 8,413 行 | 1 个 Python 文件 / 938 行 |
| 临时文件 | 每次转换一个 Chrome profile（约 18MB） | 无 |
| 主题 | SCSS 主题包，可装第三方 | 两套内置配色 |
| 演讲者视图 | 有 | 无 |

差异只列了真正有差别的维度。像"支持 Markdown 表格"这种两边都有的，不占篇幅。

需要说清一点：**mddeck 不是 marp-cli 的替代品。** 它砍掉的 PDF/PPTX 是 marp-cli 的核心卖点，
砍掉这些之后它只能覆盖"我要一个能在浏览器里翻页的 deck"这一个场景。
但如果你的场景正好是这个，mddeck 的路径短得多：一个 938 行的文件，Python 直接跑，没有依赖，没有临时目录，
而且它会在你导出之前就告诉你哪一页塞太满了。

## 六、怎么用

```bash
# 下载一个文件就够了
curl -O https://raw.githubusercontent.com/z15346183030/mddeck/main/mddeck.py

# 生成
python mddeck.py slides.md
```

真实输出（`examples/demo.md`，7 页）：

```
$ python mddeck.py examples/demo.md -o deck.html
mddeck  demo.md → deck.html
7 页 · 7.4 KB · 16 ms · 缩过字号的 0 页
  没有页面溢出
```

拥挤样本（`examples/crowded.md`，5 页，其中 2 页需要缩字号）：

```
$ python mddeck.py examples/crowded.md -o crowd.html

5 页 · 8.8 KB · 9 ms · 缩过字号的 2 页
  第 1 页  需要 532px / 可用 558px → 字号 28 → 23.0px（0.82×）

## 七、开发中踩的坑

**坑一：`.body` 是 flex item，末尾边距不会溢出。**

我最初按 CSS 常规逻辑，认为容器高度不包含最后一个子元素的 `margin-bottom`，所以测量时把末尾边距减掉了。
校准一跑，第 1 页预测 114.4px、实测 131.8px，差值 17.4px 正好是段落的 `margin-bottom`。
原因：`.body` 是 flex 容器的子项，形成了 BFC，子元素的边距被包在里面。
修法是两件事一起做——CSS 加 `.slide .body>*:last-child{margin-bottom:0}`，测量函数不再减末尾边距。
回归用例：`BuildTests.test_build_writes_html`（页面数）和 `MeasureTests.test_more_text_is_taller`（单调性）
守着这条，`FitTests.test_shrunk_page_never_exceeds_canvas` 用 4 组不同内容量守着"缩完不超画布"。

**坑二：段落没写 `line-height`，浏览器按 `normal` 算。**

测量按 1.55 算，CSS 里 `p` 根本没设行高，浏览器用 `normal`（Segoe UI 下约 1.32）。
表现是每一页都低估 5%~20%。修法：`p{line-height:1.55}`，并且把行高常量抽出来，
让测量和 CSS 用同一个数字——现在 `_css_vars()` 直接由 `TYPE` 表生成 CSS，两边不可能对不上。

**坑三：表格列宽按自然宽度算，但 CSS 里是 `width:100%`。**

表格页误差 +14.7%。原因是列宽在浏览器里被拉满整行，我按内容自然宽度算折行，
把一个本来一行的单元格算成了两行。修法：列宽一律按比例摊满可用宽度，再算折行。
另外加 0.5px 容差——浮点数累加时，`sum(char_em)*fs` 算两次可能差最后一位，
导致刚好卡在边界上的单元格多出一行。回归用例：`MeasureTests.test_narrow_box_makes_table_taller`。

**坑四：列表渲染少一个闭合标签。**

`_render_list` 原来的写法只在"遇到下一个同级项"时闭合上一个 `<li>`，最后一个永远不闭合。
90 个用例里 `test_list_closes_tags` 抓到了——`<li>` 两个、`</li>` 一个。
改成"循环结束统一闭合 + 每层缩进显式闭合"，顺带修好了 `</ul>` 的位置。

**坑五：图片路径带空格。**

行内图片的正则用 `([^)\s]+)` 取 URL，遇到 `![图](a b.png)` 直接匹配不上，原样输出。
改成 `([^)]+?)` 取到 `)` 为止，再由 `_safe_url()` 把空格编码成 `%20`。
回归用例：`InlineTests.test_space_in_path_is_encoded`。

## 八、一句话总结

marp-cli 用浏览器换来了"所见即所得"，代价是每次转换一个 18MB 的临时 Chrome、一套找浏览器的代码，
以及"这页放不下"这个它永远回答不了的问题——mddeck 反过来，不碰浏览器，但把 1280×720 里每一行算清楚，
让溢出变成一个构建时就能报错的数字。
