# fuzzrank · 2026-10-30

## 一、我拆的是哪个项目

[junegunn/fzf](https://github.com/junegunn/fzf)

- 星标：83,855
- 许可证：MIT
- 语言：Go
- 一句话定位：在终端里对一长串候选做模糊查找，边打字边把最可能的几条排到最前面。
- 为什么选它：今天的 Trending 又是清一色的 agent / skill 仓库，没有可拆的核心算法，所以走搜索 API 筛候选。fzf 满足全部硬门槛（8.3 万星、2026-10-29 还有提交、MIT、Go），而且它有一个别的项目少见的特征：**核心算法被研究得很透，但用户完全看不见它**。issue 里反复出现同一类问题——"为什么这行排在那行前面"，而答案从来不在文档里。

这不是一个"功能太多所以难用"的项目。fzf 的参数确实多（177 个），但真正的矛盾在别处：它的排序质量很好，好到用户开始依赖它，然后发现自己没法解释、没法复现、没法在自己的脚本里问一句"这一行为什么得这个分"。

## 二、它怎么做的

### 结构：一条流水线，算法在最中间

```
stdin / 命令输出
      │
      ▼
   reader.go        按行读，切成 chunk（默认 100 项一块）
      │
      ▼
   chunklist.go     维护已读/未读的块，边读边匹配
      │
      ▼
   matcher.go       每个 chunk 派一个 goroutine
      │
      ├──► algo/algo.go   ★ 唯一算分的地方
      │      FuzzyMatchV2：正向扫 → 反向收紧 → 窗口内 DP
      │      Result{Start, End, Score}
      │
      ▼
   merger.go        把多个 goroutine 的结果按分数归并
      │
      ▼
   terminal.go      8,933 行，负责画界面、收键盘、管光标
```

规模上：59 个非测试 Go 文件、740KB 源码，其中 `terminal.go` 一个人占了 8,933 行（255KB），`options.go` 110KB 里有 177 个 `case "--xxx"` 分支——一个参数一个分支。而真正决定排序的 `algo.go` 只有 1,341 行。

这个比例很说明问题：**打分算法是这套东西里最不臃肿的部分**。

### 算法：位置加成 + 局部对齐

打分模型是"对齐"而不是"包含"。查询的每个字符要落到行里的某个位置，落上去就有 16 分，另外看它前面是什么字符给加成：

| 情况 | 加成 |
|---|---|
| 前面是空格，或行首 | +10 |
| 前面是 `/ - _ . : ; ,` 这类分隔符 | +9 |
| 前面是小写、自己是大写（驼峰） | +7 |
| 前面是数字、自己是字母，或反过来 | +7 |

间隔要扣钱：开一个间隔扣 3，每多跳一个字符再扣 1。查询的第一个字符，加成翻倍。

源码注释把数值的来历写得很清楚：边界加成取 `scoreMatch / 2`（也就是 8），是为了"缩写跨过 8 个字符之后，加成刚好被间隔吃掉"。这个数字不是拍脑袋来的，是拿 web2 词典和作者自己的文件系统调出来的。

### 三步走：正向扫、反向收、窗口内 DP

2016 年的 issue #638 里，作者贴出了代码里的 FIXME：

> `// 0. (FIXME) How to find the shortest match?`
> `//    a_____b__c__abc`
> `//    ^^^^^^^^^^  ^^^`
>
> "That is fzf stops immediately when the first match is found. This gives nice O(n) time complexity but it's not guaranteed to find the best match."

第一版就是这么干的：从左往右找，凑齐所有查询字符就收工。于是查 `myfolder` 的时候，一个深埋在 `node_modules` 里的长路径会排在 `~/my_folder/foo` 前面——因为它的 `m` 出现得更早。

后来 V2 改成三步：

1. **正向扫**：从位置 0 开始依次找查询字符，找到最后一个字符时得到一个"最早结尾"。
2. **反向收**：从这个结尾往前，每个字符都取"最靠右的合法前驱"，把窗口收到最紧。
3. **窗口内 DP**：只在收紧后的窗口里跑动态规划，找分数最高的对齐。

O(n) 的扫描加上很小窗口内的 O(nm)，既保住了速度，也修掉了"第一个匹配就收工"。顺手还给单字符、双字符查询写了专用快路径，甚至有两个 6KB 的手写汇编文件（`indexbyte2_amd64.s` / `indexbyte2_arm64.s`）只为了"一次找两个字节"。

### 排序：五个 tiebreak 旋钮

分数算完之后，同分的怎么排？fzf 给了五个可选键：`chunk`（在哪一块）、`length`（行长）、`begin`（匹配起点）、`end`（匹配终点）、`index`（输入顺序），用 `--tiebreak=length,begin` 这样组合，默认是 `length`。另外还有 `--scheme=default|path|history` 三套预设，一次改一组常量。

问题就出在这两层旋钮上。下一节细说。

## 三、它哪里让人难受

### 痛点一：算出来的分数，用户拿不到

> "I'm wondering if it's possible to get fzf to print out the score given a line and prompt combination. Essentially what I'd like to do is to get the score using `--filter` or similar for just one line given a particular input."
>
> 他给的例子是 `echo "foobar" | fzf --show-score "foo"`。
>
> —— [#2113](https://github.com/junegunn/fzf/issues/2113)，2020-07-17

这条被关掉了，`--show-score` 没出现。理由可以理解：分数一旦输出就成了 API，以后改算法就是破坏兼容。但对用户来说，这意味着"为什么这行排在那行前面"永远只能靠改参数试。

### 痛点二：文档用没定义的词解释自己

> "It is confusing for someone who hasn't read fzf source code. It leaves me with these questions: what are 'additional bonus points'? There are no further mentions of it in the manpage."
>
> —— [#3387](https://github.com/junegunn/fzf/issues/3387)，2023-08-04

`--scheme` 的说明里出现了"额外的加成点"，而整本 man page 再没提过加成是什么、值多少。要搞明白只能去读 `algo.go` 的常量块。

### 痛点三：tiebreak 的名字和行为对不上

> "The command `fzf --tiebreak=end` produces with a search term of 'engine' ... I have omitted the hundred or so files in-between. The one which I would imagine should be below the second file is at the top."
>
> —— [#3837](https://github.com/junegunn/fzf/issues/3837)，2024-06-04

`--tiebreak=end` 的语义是"匹配结束位置靠后的优先"，用户理解成"文件名结尾是 engine 的优先"。名字对不上语义，用户就会得出"这个参数没用"的结论。

### 痛点四：选了字段之后，tiebreak 全部失灵

这条我用 0.74.5 实测复现了，今天仍然存在：

```
$ printf 'aur\tdockerize\naur\tsystemd-docker\ncommunity\tdocker\t5.5\n' \
    | fzf --filter=docker --nth 2 --tiebreak=length
aur	dockerize
community	docker	5.5
aur	systemd-docker
```

`community docker 5.5` 的第二个字段和查询**完全相等**，却排在 `dockerize` 后面。原因很具体：`--tiebreak=length` 量的是整行长度（22 对 14），不是被搜索的那个字段（6 对 9）。字段匹配和 tiebreak 是两套独立实现的，谁也没考虑对方。

原作者的回答是"用 `^docker$` 做精确匹配"或者"调整输入顺序"——两个都是绕过去，不是修好。

> —— [#2537](https://github.com/junegunn/fzf/issues/2537)，2021-06-23，已关闭

### 痛点五：Windows 上按 UTF-8 读标准输入

> "1. Use any system codepage other than 65001 (which is Beta and is never the default). 2. Run `dir | fzf` when any file names are present with non-ASCII characters."
>
> —— [#4065](https://github.com/junegunn/fzf/issues/4065)，至今 open

控制台写出来的是 ANSI 代码页，fzf 按 UTF-8 解，非 ASCII 文件名全变乱码。

### 小结：这些痛点有同一个形状

四个已关闭的 issue，指向同一件事：**排序这件事在 fzf 里是不可观察的**。分数是内部值，加成没有名字，tiebreak 的名字和行为对不上，字段模式下的 tiebreak 干脆量错了对象。用户能做的只有"换个参数看顺序变没变"。

这就是我们要切的口子。

## 四、我们做了什么

**一句话定位：一个只做排序、并且把排序过程完整打印出来的过滤器。**

### 砍了什么、留了什么、加了什么

| 砍掉 | 为什么 |
|---|---|
| 交互式终端界面（8,933 行） | 过滤器不需要接管键盘。没有 TUI 就没有光标、没有重绘、没有 Windows 控制台的 ANSI 兼容问题——#1526、#1766、#4260、#3346 那一串 issue 全部消失 |
| 预览窗口、按键绑定、shell 集成 | 那些是"选"的功能，我们只做"排" |
| 177 个参数 → 12 个 | 每个参数都是一个要解释、要测试、要兼容的决定 |
| `--tiebreak` 旋钮 | 换成一条固定链 |
| `--scheme` 三套预设 | 一套常量。路径和历史的差别用字段模式表达就够了 |
| SIMD 汇编快路径 | 这是 fzf 快 2–7 倍的主因，也是我们明确认输的地方 |

| 留下 | 为什么 |
|---|---|
| 位置加成模型 | 这是模糊查找好用的全部原因。去掉它，`fzb` 就匹配不上 `foo_bar` |
| 双向收紧窗口 | 没有它就会退回 #93 那种"第一个匹配就收工" |
| `--filter` 批处理语义 | 唯一能在脚本里用的模式，也是原版最少打磨的模式 |
| 字段选择 | 表格数据太常见，砍掉等于砍掉一半用途 |

| 加上 | 对应哪个问题 |
|---|---|
| `--explain` 逐字符账单，各项之和恒等于总分 | #3387，加成终于有名字 |
| `--explain-line '某一行'`，不读输入直接解释单行 | #2113 那个"只想问一行"的诉求 |
| `--score` 前缀输出 | #2113，分数可以拿去排序了 |
| 单一排序链，字段模式下 tiebreak 量的是字段 | #2537、#3837 |
| `--limit` 用堆，内存恒定 34MB | 原版必须收齐所有匹配才能排序 |
| 编码自动识别，输出沿用输入编码 | #4065 |
| 输出强制 LF | Windows 上 `\r\n` 会让 `| head`、`diff` 的下游全部错位 |

### 核心算法：拿 `fzg` 匹配 `src/algo/fuzzy.go` 走一遍

**第一步，正向扫。** 从 0 开始依次找 `f`、`z`、`g`，`g` 落在 15，这个匹配最早在 15 结束。

**第二步，反向收。** 从 15 往前，先找 `z`（在 11），再找 `f`（在 9）。窗口锁在 9..15，长度 7。不收紧的话窗口会从 0 开始，跨度和加成都会算错。

**第三步，窗口内对齐打分。**

| 位置 | 字符 | 计算 | 得分 |
|---|---|---|---|
| 9 | `f` | 匹配 16 + 分隔符 `/` 后加成 9 × 2（首字符翻倍） | +34 |
| 10 | — | 跳过 `u`，间隔 1 个字符 | −3 |
| 11 | `z` | 匹配 16 + 词内无加成 | +16 |
| 12 | — | 跳过 `z y .` 三个字符，间隔封顶 | −5 |
| 15 | `g` | 匹配 16 + `.` 后加成 9 | +25 |

合计 48 + 27 − 8 = **67**。这就是 `--explain` 打出来的那张表，和 `--score` 输出的数字出自同一个函数。

### 连续段的加成是递增的，不是固定的

这一点和 fzf 不一样，而且是被测试逼出来的。

如果连续段固定只给 +4，那么查 `abc` 时：

- `abc`：48（匹配）+ 20（首字符）+ 4 + 4 = **76**
- `a_b_c`：48 + 20 + 9 + 9 − 3 − 3 = **80**

缩写赢了。这不是小数，这是"所有缩写都会赢过它缩写的那个词"——查 `fzg` 永远先出 `fzf_test.go` 而不是 `fuzzy.go` 的同类问题。

改成递增（4、8、12，之后封顶 12）之后：

- `abc`：48 + 20 + 4 + 8 = **80**
- `a_b_c`：48 + 20 + 9 + 9 − 3 − 3 = **80**

打平，然后由"跨度更短者优先"判给 `abc`。查 `fuzzy` 匹配 `fuzzy.go` 时五个字符连着，加成 4+8+12+12 = 36，加上首字符 20，总分 134。

### 排序只有一条链

1. **分数** —— 高的赢。
2. **跨度** —— 匹配区域越短越好。同样分数下，紧凑的那个更可能是想找的。
3. **行长** —— 行越短越好。同样的匹配，周围东西越少越聚焦；在路径上，这就是"文件名里带查询词"的那一条。
4. **起点** —— 越靠前越好。
5. **输入顺序** —— 完全相同的行保持原顺序。

没有旋钮。`--explain` 会明确写出这一次是哪一环决定了胜负，比如 `ordered above #2 by line length 6 vs 9`。

第 3 条是调过的。最早我把"起点"排在"行长"前面，结果查 `sqlite3` 时：

```
190  py/Lib/sqlite3/dump.py
190  py/Lib/dbm/sqlite3.py      ← 文件名里就是 sqlite3，却排第二
```

五条路径分数完全一样（同样的对齐、同样的跨度），差别只在起点和行长。人想找的是 `sqlite3.py` 这个文件，而它所在的路径更短。把行长提到起点前面之后，`dbm/sqlite3.py` 就上去了，和 fzf 的默认行为也一致了。

## 五、和原版差在哪

| 维度 | fzf 0.74.5 | fuzzrank |
|---|---|---|
| 形态 | 交互式选择器 | 批处理过滤器 |
| 代码规模 | 59 个非测试 Go 文件、740KB，含手写汇编 | 1 个 Python 文件、697 行，纯标准库 |
| 命令行参数 | 177 个 | 12 个 |
| 分数可见性 | 内部值，无输出途径 | `--score` 输出、`--explain` 逐项列出 |
| 排序规则 | 5 个 tiebreak 旋钮 | 1 条固定链，5 个环节 |
| 字段模式下的 tiebreak | 量整行 | 量被搜索的字段 |
| 匹配质量（40 条标注查询） | top-1 37/40，MRR 0.956 | top-1 38/40，MRR 0.969 |
| 1M 行耗时（`fzg`） | 0.36 s | 2.33 s |
| 1M 行内存（`fzg`） | 181 MB | 34 MB |
| 1M 行内存（`-l 10`，`a` 查询） | 385 MB（无此模式） | 34 MB |
| 非 UTF-8 输入 | 按 UTF-8 解，乱码（#4065 open） | 试解 UTF-8，失败回退系统代码页 |
| Windows 换行 | 原样输出 | 强制 LF |
| 启动开销 | 64 ms | 526 ms（其中 415 ms 是解释器本身） |

匹配质量那一行要说明白：这 40 条查询的答案按"唯一一个文件名里带这个词的路径"构造，本身偏向短路径，而"行长"正好是我们的第 3 个 tiebreak。所以 38 比 37 这点差距**不能当成我们更强**，它只说明两边在同一个水平上——真正的证据是另一件事：8 组基准里，两个工具的命中条数逐条完全一致（18、319、188、4497、3689、65316、106263、936026）。

速度上我们输了 2–7 倍，这个没法洗。Go 加手写汇编，Python 加纯标准库，差距就是这么大。换来的是另外两件事：小结果集时内存少 5 倍，以及 `--limit` 之后内存完全不随匹配数增长——`fzf --filter` 必须收齐所有匹配才能排序，查 `a` 这种高频词要吃到 385MB，我们恒定 34MB。

## 六、怎么用

零配置，`python fuzzrank.py` 就能跑。

```bash
$ python fuzzrank.py tkn examples/paths.txt
src/tokenizer.go
test/tokenizer_test.go
```

`tkn` 和 `tokenizer` 在字母表上一点都不挨着，但它是 `tokenizer` 的子序列，而且两个匹配都落在词首，这就够了。短的那条赢了 tiebreak。

问分数：

```bash
$ python fuzzrank.py -q algo -s -l 4 examples/paths.txt
106	src/algo/fuzzy.go
106	src/algo/normalize.go
106	src/algo/algo_test.go
78	src/terminal.go
```

前三条都是 106 分——同样的五个字符、同样的词首、同样的跨度——所以由 tiebreak 决定，行长把 `src/algo/fuzzy.go` 推到了第一。

问"为什么"：

```bash
$ python fuzzrank.py -q fuzzy --explain examples/paths.txt
#1  score 134  span 5  start 9  chars 17  line 1
    src/algo/fuzzy.go
    query 'fuzzy'
     pos  points  why
       9     +34  match 16 + word start 9 x2
      10     +20  match 16 + run 1, +4
      11     +24  match 16 + run 2, +8
      12     +28  match 16 + run 3, +12
      13     +28  match 16 + run 4, +12
    ---- -------  ---------------------------------------------
    total  134 = 80 match + 54 bonus - 0 gap
    rank 1 of 1
```

只要一行，不读输入：

```bash
$ python fuzzrank.py -q fzg --explain-line 'src/algo/fuzzy.go'
#1  score 67  span 7  start 9  chars 17  line 1
    src/algo/fuzzy.go
    query 'fzg'
     pos  points  why
       9     +34  match 16 + word start 9 x2
      10      -3  skipped 1 char
      11     +16  match 16 + inside a word
      12      -5  skipped 3 chars
      15     +25  match 16 + word start 9
    ---- -------  ---------------------------------------------
    total   67 = 48 match + 27 bonus - 8 gap
    rank 1 of 1
```

查表格的某一列：

```bash
$ python fuzzrank.py -q docker -n 2 -s examples/packages.txt
164	community	docker	5.5
164	aur	dockerize
164	extra	docker-compose	2.24
162	aur	systemd-docker
```

`community docker 5.5` 的第二个字段和查询完全相等，排第一。这就是 fzf 在 #2537 里做不到的那件事——因为我们的 tiebreak 量的是这个字段（6 个字符），不是整行（22 个字符）。

接管道也行，退出码能直接用：

```bash
$ git ls-files | python fuzzrank.py -q test -l 3 && echo "found"
```

`0` 有匹配，`1` 没匹配，`2` 参数错。没匹配不算崩溃，脚本不用解析输出就能分辨。

## 七、开发中踩的坑

九个真坑，五个是被测试或真实数据打出来的。

**1. `--limit` 保留了最差的 N 条。** `heapq` 是最小堆，我要的是"留最好的 N 条"，写成了 `if item < heap[0]: heapreplace`。结果 `heap[0]` 一直是最好的一条，后来的好结果永远挤不进去，最后留下的是最差的那几条。查 `item1` 时 `item1`（重复行）被 `item10` 挤掉了。修法是把键全部取负，让最小堆的 `heap[0]` 变成最差的一条。回归测试 `test_limit_equals_the_top_of_a_full_sort` 拿 300 行随机语料、5 个查询，比对"全排序取前 7"和"`limit=7`"的结果。

**2. 缩写赢过它缩写的词。** 见上一节。连续段固定 +4 的时候 `a_b_c` 以 80:76 赢过 `abc`。改成递增 4/8/12 之后打平，靠跨度判给 `abc`。回归测试 `test_acronym_does_not_beat_the_plain_substring`。

**3. `dataclasses` 让启动多花 230ms。** 用 `-X importtime` 一看，`dataclasses` 自己 46ms，累计 271ms——它把 `inspect`、`subprocess`、`tempfile` 全拖进来了。我那两个结构体只是"带默认值的不可变元组"，换成 `NamedTuple` 之后 `--version` 从 772ms 降到 526ms（裸解释器 415ms）。对一个命令行过滤器，这是 32% 的体感差距。

**4. 每条匹配都构造对象，慢了 4 倍。** 第一版每算一个候选就构造一组 `Part` 对象（为了 `--explain` 能打印）。1M 行查 `tests/test` 要 19.5 秒，cProfile 显示 `score_positions` 一个人占 4.23 秒里的绝大部分。拆成两条路径：`score_fast` 只返回整数，`score_parts` 才建对象（只在 `--explain` 时对前几条调用）。降到 4.35 秒。两条路径会不会漂移？加了 `test_fast_and_explained_scores_agree`，400 组随机字符串逐条比对——如果哪天漂了，`--explain` 打出来的表就对不上排序用的分数。

**5. Windows 上输出 `\r\n`。** 所有 CLI 测试一起红，报的都是 `'abc\r\n' != 'abc\n'`。Python 在 Windows 上会把 `\n` 翻译成 `\r\n`，对终端无害，对管道有害——`| head`、`diff`、任何比对字节的下游都会错位。`sys.stdout.reconfigure(newline="\n")` 解决。

**6. argparse 分不清"查询"和"文件"。** `fuzzrank -q alp file.txt` 里，`file.txt` 被塞进了 positional 的 `query`，`files` 是空的，于是程序去读了空的标准输入，静默返回 1。这个坑很阴——不报错，就是没结果。改成单个 `items` 列表手动切分：有 `-q` 时第一个词就是文件，没有时第一个词才是查询。

**7. 编码检测把短输入判错。** 检测逻辑里我写了"坏字节靠近缓冲区尾部就不算证据"，本意是躲开"多字节字符被 64KB 边界切断"的假阳性。结果 `caf\xe9`（5 个字节）的坏字节就在最后，被判成 UTF-8，输出变成 `caf�`。改成只有"peek 满 64KB 且坏字节在尾部"才认为是截断。这条的测试最后变成了 skip——因为这台机器的系统代码页就是 UTF-8，自动回退和直接按 UTF-8 解没有区别，只有显式 `--encoding` 那条路径还能测。这一点我写进了 README，没有假装测过。

**8. 字段模式把整行替换成了字段。** 加 `--field 2` 的时候，输出变成了 `docker` 而不是 `community\tdocker\t5.5`。原因是打分用的文本和输出的文本共用了同一个字段。拆成两个：`text` 是被搜索的文本（可能是某个字段），`line` 是原始行，永远输出后者。

**9. `fzg` 匹配 `fzf_test.go` 排在 `fuzzy.go` 前面。** 我以为是自己算法出了问题，查了半天。后来拿真 fzf 一跑：

```
$ fzf --filter fzg < examples/paths.txt
test/fzf_test.go
src/algo/fuzzy.go
```

一样的顺序。这不是 bug，是这套打分模型的固有性质：`f`、`z` 相邻给了一次连续加成，`g` 又落在词首，加起来赢过了"更紧凑但更分散"的 `fuzzy.go`。既然参考实现也是这个结果，就不改，写进报告里。

## 八、一句话总结

fzf 把模糊查找的排序做到了很好，却让它变成了一个只能相信、不能追问的黑盒；fuzzrank 放弃了它的界面、它的 177 个参数和它 2–7 倍的速度，只为了把那个分数拆成一张能对得上账的表。
