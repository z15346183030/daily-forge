# squeeze · 2026-10-20

把喂给大模型的 JSON 和日志压小，省 60-87% 的 token，但一个错误都不丢。

---

## 一、我拆的是哪个项目

**[headroomlabs-ai/headroom](https://github.com/headroomlabs-ai/headroom)** — 76,324 星，Apache-2.0，Python。

它干的事一句话说清：**在你的提示词送进大模型之前，把里面的工具输出、日志、RAG 片段压缩掉。**

为什么这事值 76k 星？因为上下文窗口虽然在涨，但涨得没有 agent 产生的数据快。一个 coding agent 跑十几轮工具调用，光日志和文件内容就能把窗口撑爆。压缩不是锦上添花，是刚需。

**为什么选它：** 星标够高（需求被验证）、许可证干净、核心价值（去冗余）能用纯算法实现、而且它明显过度工程化了——一个压缩需求做成了四种接入形态。

---

## 二、它怎么做的

它的架构是这样的：

```
你的 agent
   ↓ 提示词、工具输出、日志、RAG 结果
┌──────────────────────────────┐
│  ContentRouter（判断类型）    │
│    ├─ SmartCrusher   → JSON  │
│    ├─ CodeCompressor → 代码  │
│    └─ Kompress-v2    → 散文  │
│  CacheAligner（缓存对齐）     │
│  CCR（原始内容本地缓存）       │
└──────────────────────────────┘
   ↓ 压缩后的提示词 + 一个「取回原文」工具
大模型
```

有三个设计决策我认为是对的：

**第一，按内容类型分流。** JSON、代码、散文的最优压缩策略完全不同。JSON 是结构冗余（每行重复同样的 key），代码是语法冗余，散文是语义冗余。用一套逻辑通吃，效果必然平庸。

**第二，可逆。** 原始内容存在本地，模型需要细节时能调 `headroom_retrieve` 拿回原文。这把「有损压缩」变成了「按需无损」，很聪明。

**第三，每种接入形态都铺了。** 库、代理、`wrap` 命令包装、MCP server。不管你用什么工具，都有一条路能接上。

## 三、它哪里让人难受

**痛点一：装上去容易，拆下来是场寻宝。**

> "The pieces to undo a Headroom install exist, but they're fragmented and undocumented — so a full teardown is a multi-command scavenger hunt."
> —— [issue #748](https://github.com/headroomlabs-ai/headroom/issues/748)

要完整卸载，得依次敲 `headroom unwrap codex`、`headroom unwrap claude`、`headroom mcp uninstall`、`headroom install agent remove`，再手动 `pip uninstall`。

**这说明一个根本问题：`wrap` 会改你的 agent 配置。** 对一个只想压一下日志的人来说，这个代价完全不成比例。

**痛点二：判断「这是什么内容」用了个 ML 模型，结果在 Windows 上直接挂死。**

> "`headroom._core.detect_content_type()` hangs on Windows with `headroom-ai 0.24.0` and Python 3.13. This makes `headroom_compress` unusable for any content large enough to enter the real compression path."
> —— [issue #845](https://github.com/headroomlabs-ai/headroom/issues/845)

判断内容类型这一步，用的是 ONNX 上的 magika 模型。这个依赖在 Windows + Python 3.13 上会挂起，导致整条压缩链路不可用。

**这是一个典型的过度设计**：判断「这是 JSON 还是日志」，一行 `json.loads()` 试探加几个正则就够了，不需要神经网络。引入模型换来的是几百 MB 依赖和跨平台兼容地狱。

**痛点三：代理模式不稳定。**

[#3259](https://github.com/headroomlabs-ai/headroom/issues/3259) 报告 proxy 在连接上游时挂 180-220 秒然后 502；[#980](https://github.com/headroomlabs-ai/headroom/issues/980) 是 Docker 网络下同步 DNS 阻塞事件循环。

代理是个强大的形态，但它把网络问题也一起引入了。

**痛点四：八个概念，每个都有坑。**

库 / 代理 / wrap / MCP / 跨 agent 记忆 / `learn` / 输出 token 压缩 / CCR。文档跟不上，[#207](https://github.com/headroomlabs-ai/headroom/issues/207) 直接就是「多个文档问题」。

## 四、我们做了什么

**定位一句话：一个不需要安装、不需要配置、不会碰你任何文件的命令行工具。**

### 砍掉的

| 砍掉 | 为什么 |
|---|---|
| ML 内容识别 | #845 的根因。改成 `json.loads` 试探 + 日志正则，够用且不会挂 |
| 代理模式 | 引入端口、DNS、超时一整套故障面。CLI 读写文件已覆盖绝大多数场景 |
| wrap / MCP / 库 | 都要改别人的配置。一个 CLI 什么都不用改 |
| AST 代码压缩 | 收益不稳定，破坏语义风险高，不如不做 |
| reversible cache | 留原文件就行，多一层缓存多一层要维护的状态 |

### 保留的

按类型分流压缩（这是核心思路）、压缩率统计、错误行保护。

### 自己加的

**行数预算下的关键行免疫。** 原版没有行级截断，所以没这个问题。我们加了 `--max-rows`，但规定 `ERROR` / `WARN` / `FATAL` / `CRITICAL` 不受预算约束。

### 它是怎么压的

**JSON：把「每行重复的 key」提到表头。**

压缩前，80 条用户记录，每条都重复写 `"id"`、`"username"`、`"email"` 这些字段名：

```json
[{"id":0,"username":"user_000","email":"user0@example.com","role":"dev",...},
 {"id":1,"username":"user_001","email":"user1@example.com","role":"admin",...},
 ...]
```

压缩后：

```
# 80 行 × 7 列: id, username, email, role, active, created_at, bio
0 | user_000 | user0@example.com | dev | true | 2026-07-10T08:00:00Z | 这是一个很长的个人简介…
1 | user_001 | user1@example.com | admin | true | 2026-02-15T08:00:00Z | 这是一个很长的个人简介…
```

字段名从出现 80 次变成出现 1 次。这就是 60% 的压缩率从哪来的。

**日志：先丢噪音，再折叠重复，最后按预算截断。**

1. `TRACE` / `DEBUG` 直接丢（占典型日志的 60%），并在头部说明丢了多少
2. 连续重复的行折叠成 `×N`——判断依据是把数字、UUID、十六进制都抹平成占位符后比较
3. 超过行数预算时，只保留头尾，中间省略并标注

## 五、和原版差在哪

| 维度 | headroom | squeeze |
|---|---|---|
| 安装 | pip / npm，带 ML 依赖 | 无。下载一个 `.py` 文件 |
| 依赖 | magika、onnxruntime、fastapi | 标准库，零依赖 |
| 配置 | 要 wrap / proxy / MCP 配置 | 零配置 |
| 改你的文件 | `wrap` 会改 agent 配置 | 完全不碰 |
| 内容识别 | ML 模型（Windows 会挂） | 正则试探（不会挂） |
| 可逆 | 本地缓存 + retrieve | 自己留原文件 |
| 代码量 | 94 MB 仓库 | 约 380 行 |

## 六、怎么用

```bash
git clone https://github.com/z15346183030/squeeze && cd squeeze

python squeeze.py big_response.json --stats
# [squeeze] 类型=json  字符 15755→5025  token≈6818→2700  省 60.4%

cat app.log | python squeeze.py - --stats
# [squeeze] 类型=log   字符 20739→2343  token≈5193→670   省 87.1%
```

## 七、开发中踩的坑

第一版的 `--max-rows` 逻辑是盲目砍掉中间行。测试用的日志里，`FATAL` 正好在第 200 行，被砍掉了。

**一个压缩日志的工具，把唯一那条有用的错误吞了——这种工具不如不用。**

发现后重写了截断逻辑：先把关键行挑出来锁定，剩余预算再分给头尾。加了两个回归测试锁住这个行为：

- `test_critical_lines_survive_middle_truncation` — 200 行日志、10 行预算、FATAL 在第 100 行，必须保留
- `test_all_errors_kept_even_when_budget_is_small` — 30 行全是 ERROR、预算只有 5 行，一行都不能丢

---

## 八、一句话总结

headroom 把「压缩上下文」做成了一个平台，squeeze 只把它做回一个工具。

**当你想压一下手头这份数据时，你需要的是后者。**
