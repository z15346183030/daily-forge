# astdiff · 2026-10-25

## 一、我拆的是哪个项目

[**Wilfred/difftastic**](https://github.com/Wilfred/difftastic)

- 星标：26,057
- 许可证：MIT
- 语言：Rust
- 一句话定位：一个按语法结构比较代码的 diff 工具，重排缩进、折行、改引号这些不动语义的改动不会淹没真正的改动。

**为什么选它。**

第一，它解决的问题是真实的。任何做过 code review 的人都知道那种痛苦：一个提交 400 行，其中 380 行是把参数换行、把引号统一、把一个函数从文件头挪到文件尾。真正改动逻辑的那 20 行埋在里面，得一行一行翻。

第二，它的核心思路足够清晰，清晰到能讲明白。README 里只有一句话：「Difftastic treats structural diffing as a graph problem, and uses Dijkstra's algorithm.」不用先理解一堆领域概念就能看懂它在干什么。

第三，它的痛点非常具体，而且**是架构性的，不是 bug**。这一点很关键——如果一个项目的毛病只是「有个函数写错了」，那我们做一个精简版没有意义；只有当它的毛病来自「为了支持 30 种语言所以必须这么设计」时，砍掉那 30 种语言才是真的解决问题。

第四，MIT 许可证，可以放心读代码、看设计，不用担心污染。

硬性门槛全部满足：26,057 星远超 1000；最近一次提交是 2026-10-16，九天前；MIT；Rust；issue 里有大量「这个输出看不懂」「为什么不支持 X」的反馈。

## 二、它怎么做的

### 一句话原理

把两个文件的语法树各自压平成一串 token，然后在这两串 token 上找一条最短的编辑路径。

### 核心链路

```
源文件
  │
  ├─ tree-sitter 解析（30+ 种语言，语法编译进二进制）
  │
  ▼
语法树
  │
  ├─ 深度优先遍历，压平成 token 序列
  │    每个节点变成 开括号 / 子节点... / 闭括号
  │
  ▼
两个 token 序列
  │
  ├─ Dijkstra 寻路
  │    状态 = (左序列走到第 i 个, 右序列走到第 j 个)
  │    边   = 左 i 前进一格（代价高）/ 右 j 前进一格（代价高）/ 两边同时前进（代价低）
  │    目标 = 从 (0,0) 走到 (n,m) 的最低代价路径
  │
  ▼
匹配上的 token 对
  │
  ├─ 每个 token 记得自己原来在第几行 → 推导出「旧第 3 行 ↔ 新第 11 行」
  │
  ▼
并排显示（sliders 负责让两边的行看起来对得上）
```

这个设计里最聪明的一步是**把树 diff 转成序列 diff**。树编辑距离是出了名的难写（复杂度和实现难度都高），而序列上的最短路径有现成算法。代价是丢掉了树的结构信息——这个代价后来变成了 issue #587，后面会讲。

第二步聪明的地方是**行号跟着 token 走**。它不需要单独做行对齐，对齐是从 token 匹配结果里自然长出来的。

## 三、它哪里让人难受

### 1. 在 Python 里，它会把缩进变更报成「没有变化」

issue [#587](https://github.com/Wilfred/difftastic/issues/587)，open，11 条评论，2023-10-25 开的，到今天快三年了还没关。

报告人写得很克制：

> I verified via `--dump-syntax` that ASTs are significantly different.

复现是这样的：

```python
# a.py
def test(a, b):
    if a:
        print(a)
        if b:
            print (b)

# b.py
def test(a, b):
    if a:
        print(a)
    if b:
        print (b)
```

`print(b)` 从「只有 `a` 为真时才执行」变成了「无条件执行」。`diff -u` 老老实实说 2 行变了。而 `difft` 的输出是：

```
b.py --- Python
No syntactic changes.
```

这不是一个能靠打补丁修好的 bug。根因在架构里：**把树压平成 token 序列的那一步，丢掉了父子关系**。

对 Rust、JS 这类靠花括号定界的语言，父子关系有冗余表达——花括号本身就在 token 流里，`{` 和 `}` 的位置变了，序列就变了。但 Python 的块边界是缩进，缩进不产生 token。`if b:` 从 `if a:` 里面挪出来之后，token 序列一模一样：

```
open If, N:a, open Expr, Call:print, N:a, close, open If, N:b, open Expr, Call:print, N:b, close, close
```

挪出来之后还是这一串。序列一样，Dijkstra 当然认为没有改动。

**这就是「为了通用而牺牲精确」的代价。** 一个支持 30 种语言的工具，只能用所有语言共有的那部分信息；而对 Python 来说，最重要的那部分信息恰好不在里面。

### 2. 纯排版变化要么全显示，要么全消失

issue [#637](https://github.com/Wilfred/difftastic/issues/637)，open，7 条评论：

> When there's only a non-syntactic diff (eg whitespace in perl, java, python source code), difft shows `no syntactic changes`. However, for usage with `git diff`, I would like to see even those changes.

用 `GIT_EXTERNAL_DIFF` 接管 `git diff` 之后，一个只改了空格或者只改了注释的提交会输出「没有语法变化」，然后什么都不显示。

问题在于**两件事被塞进了同一个开关**：语义变更和排版变更。要么都算变更（那就退回普通 diff 的噪音水平），要么都不算（那就看不见任何东西）。没有中间态。

而实际上人的需求是分层的：我想先看「有没有真的改逻辑」，确认没有之后，再决定要不要看「排版动了哪里」。

### 3. git 多传一个参数就中断整个 diff

issue [#952](https://github.com/Wilfred/difftastic/issues/952)，open，5 条评论，2026-02-18：

> error: Difftastic does not support being called with 8 arguments.
> USAGE: difft [OPTIONS] OLD-PATH NEW-PATH
> fatal: external diff died, stopping

`git difftool --cached` 在某些工作区状态下会多传参数，然后整个 diff 就死了。同类诉求还有 [#280](https://github.com/Wilfred/difftastic/issues/280)（希望能当 `git add -p` 的 diff filter），2022 年开的，到现在还是 open。

一个被设计成「接管 git diff」的工具，在最常见的 git 用法上会崩——这属于集成边界没做扎实。

### 4. 仓库体积和稳定性

issue [#343](https://github.com/Wilfred/difftastic/issues/343)，open，8 条评论：

> Git respository has grown to 1.24 GiB
> This is too much. It makes CI slower and contributing slower.

为了支持 30 多种语言，仓库里 vendored 了 38.95 MB 的 tree-sitter 语法（git 历史里更大）。而 README 的 Known Issues 第一句就是：

> Performance. Difftastic scales relatively poorly on files with a large number of changes, and can use a lot of memory.
> Robustness. Difftastic regularly has releases that fix crashes.

崩溃类 issue 一直有新的：[#770](https://github.com/Wilfred/difftastic/issues/770)（`Hunk lines should be present in matched lines` panic）、[#702](https://github.com/Wilfred/difftastic/issues/702)（`index out of bounds`）。还有 [#227](https://github.com/Wilfred/difftastic/issues/227) 那种「对齐看起来不对」的显示问题——`src/display/sliders.rs` 整整 26 KB 代码就是在处理「两边的行怎么摆才看起来对得上」，仍然会出错。

## 四、我们做了什么

### 定位

**一个只认 Python 的结构 diff：缩进算数，排版单独算，参数只有 9 个。**

### 砍了什么、留了什么、加了什么

| | 内容 | 理由 |
|---|---|---|
| **砍** | 30 多种语言的 tree-sitter 语法 | 一天做不完，而且 38.95 MB 的语法文件正是 #343 的成因 |
| **砍** | Dijkstra 寻路 | 状态空间大、内存不可控。换成 Myers 最短编辑路径，结果同样是最优 LCS，但代价模型简单、内存可控 |
| **砍** | 语法高亮、`--dump-syntax`、DOT/HTML 输出 | 和「看清改了什么」无关 |
| **砍** | 22 个参数 + 20 个环境变量 | 收敛到 9 个参数，0 个环境变量，0 个配置文件 |
| **砍** | sliders 那套对齐算法 | 26 KB 换来的还是「看起来不对」。改成从 token 匹配直接推导行槽位 |
| **留** | 语法树 → token 序列 → 序列比较这条主干 | 这是原版最正确的设计决策，绕开它没有更好的办法 |
| **留** | 解析失败退回逐行 diff | 宁可退化，不给假结论 |
| **留** | side-by-side 显示 | 结构 diff 的结论本来就适合并排看 |
| **加** | **嵌套深度参与判定** | 直接解决 #587 |
| **加** | **格式变更单独计数、默认折叠** | 直接解决 #637 |
| **加** | **7/8/9 个参数都认** | 直接解决 #952 |
| **加** | 改名提示 | 旧名整体消失 + 新名整体出现 → 一行提示 |
| **加** | 移动检测 | 整段内容原样出现在别处 → `↔`，不算删除 + 新增 |

### 核心算法

三步。

**第一步：把语法树压平成带深度的 token 序列。**

每个节点展开成 `open`（进入）、子节点、`close`（离开），叶子节点直接变成原子。每个 token 记三样东西：类型、行号、**嵌套深度**。

```python
def available(warehouse, reserved):
    stock = WAREHOUSES.get(warehouse, 0)
```

变成：

```
open FunctionDef:available    depth=1  line=6
  atom D:available            depth=2  line=6
  open arguments              depth=2  line=6
    atom P:warehouse          depth=3  line=6
    atom P:reserved           depth=3  line=6
  close arguments             depth=2  line=6
  open Assign:stock           depth=2  line=7
    atom N:stock              depth=3  line=7
    open Call:WAREHOUSES.get  depth=3  line=7
      atom A:get              depth=4  line=7
      atom N:WAREHOUSES       depth=4  line=7
      ...
```

`open` 标签带名字（`FunctionDef:available`、`Call:WAREHOUSES.get`、`Assign:stock`）是必须的。不带的话，`open arguments` 这种 token 在文件里出现几百次，序列比对会张冠李戴——开发过程中真的出现过：`WAREHOUSES = {...}` 被配成 `rows = []`，只因为两行都以 `open Assign` 开头。

**第二步：跑最短编辑路径。**

Myers 算法，O(ND)，D 是编辑距离。两份文件一样时 D=0，一遍扫过去就完事；只有几处改动时 D 很小。D 超过阈值（默认 2000）时退回 `difflib` 的分块匹配，并在输出里注明「差异过大，改用近似匹配」。

**第三步：从 token 匹配推出行对齐。**

每个匹配对 `(i, j)` 贡献一条「旧第 3 行 ↔ 新第 11 行」的证据。按行聚合：

- 一行的所有 token 都匹配上了，**且深度没变** → 没变
- 一行的所有 token 都匹配上了，**但深度变了** → `↕` 缩进变更
- 一行匹配到多个新行 → 折行，算格式变更
- 几个旧行匹配到同一个新行 → 合并，算格式变更
- 有 token 没匹配上 → `~` 语义变更

然后只保留两边都单调递增的行对（否则并排会错位），剩下的交给移动检测。

**深度这一步就是全部差异所在。** 原版把树压平之后只比序列；我们在压平的时候把深度记下来了，比较完之后回头检查「这些配上的 token，深度还一样吗」。不一样就说明这行代码换了嵌套层级——在 Python 里，这就是换了所属的代码块，也就是改了行为。

### 具体例子：一次真实的重构

`examples/before.py` 和 `examples/after.py` 是同一个小模块的两版。改动内容：

1. 把 `report` 函数挪到文件开头
2. 把 `WAREHOUSES` 字典折成多行
3. 把 `stock` 改名成 `on_hand`（3 处）
4. 把 `return {...}` 折成多行
5. 把 `if left < order["qty"]` 改成 `<=`

`git diff --numstat` 的结论：**新增 21 行，删除 13 行**，合计 34 行变更。

`astdiff` 的结论：

```
── 语义 4 行 · 移动 5 行 · 格式 2 行 · 未变 6 行
```

那 4 行语义变更里，3 行是同一个变量改名，真正动了逻辑的只有 1 行。剩下的 30 行是排版和位置。

再举一个更极端的。拿 CPython 的 `argparse.py`（2690 行），用 `ast.unparse` 整个重排一遍——相当于有人把你的代码全选、格式化、重新换行、顺手删掉所有注释：

```
$ git diff --no-index --numstat arg_a.py arg_fmt.py
117     1051    arg_a.py => arg_fmt.py

$ python astdiff.py --stat arg_a.py arg_fmt.py
arg_a.py → arg_fmt.py
  语义变更      0 行
  缩进变更      0 行
  位置移动      0 行
  纯格式      454 行
  新增          0 行
  删除          0 行
  未变       1237 行
```

行级 diff 报了 1168 行变更，结构 diff 说一行语义都没变。这是对的——`ast.unparse` 不改变语法树。那 454 行格式变更里，大部分是被 `unparse` 丢掉的注释。

## 五、和原版差在哪

| 维度 | difftastic | astdiff |
|---|---|---|
| 语言支持 | 30+（tree-sitter） | 1（Python 标准库 `ast`） |
| 依赖 | Rust 工具链 + 38.95 MB vendored 语法 | 无，纯标准库 |
| 分发 | 单二进制（含全部语法） | 一个 `.py` 文件，921 行 |
| 缩进变更 | 忽略（#587） | `↕` 标出，`--check` 退出码 1 |
| 纯排版变更 | 和语义变更共用一个开关（#637） | 单独计数，默认折叠 |
| diff 算法 | Dijkstra 寻路 | Myers 最短编辑路径 |
| 行对齐 | 从匹配推导 + sliders（26 KB） | 从 token 匹配直接推出行槽位 |
| git 传参 | 只认 7 个（#952 会崩） | 7 / 8 / 9 个都认 |
| 参数 | 22 个长参数 + 20 个环境变量 | 9 个参数，0 个环境变量 |
| 源码规模 | 32 个 Rust 文件 / 527 KB | 1 个 Python 文件 / 921 行 |
| 改名提示 | 无 | 有（全局改名才提示） |
| 移动检测 | 无（明确「order matters」） | 有 |
| 崩溃处理 | panic 时有（#770、#702） | 解析失败退回行级，不 panic |
| 生成 patch | 不做（明确非目标） | 不做（明确非目标） |

**没变的：** 不生成 patch。这是原版明确划的边界，我们也认。AST diff 是有损的，它不知道空白该怎么还原，硬要生成 patch 只会出错。要 patch 请用 `diff`。

## 七、开发中踩的坑

这次踩的坑比前几个项目都深，值得记下来。

### 坑一：Myers 算法写错了两处，而且错得很隐蔽

第一版跑出来，1865 行的文件里有 178 行被标成「移动」，明明只改了一个函数名。

我先用随机序列对着动态规划算出来的真 LCS 校验，结果 3000 组里有 800 组不对。两处错误：

**第一处：越界的对角线没有标记为「不可达」。** 当 `x` 超过左边序列长度时，这条路径已经不可能了，但我只是 `continue` 跳过去，`v[k]` 里还留着上一轮的值。下一轮读这个值时，就把「不可能的路径」当成了可行路径。改成显式写入 `-10^9` 之后才对。

**第二处：漏了 `d = 0` 那一段对角线。** 回溯循环写的是 `for d in range(final_d, 0, -1)`，走到 `d = 1` 就停了，剩下从 `(0,0)` 到当前点的那段纯对角线没有收集。结果是「公共前缀整段丢失」——`['a','b']` 和 `['a','b','c']` 比出来是空的。

回归测试：`test_match.py::MyersTest::test_tail_snake_is_kept`、`test_matches_true_lcs_length`（200 组随机序列对着 DP 校验）。

### 坑二：token 标签不带名字，序列比对会张冠李戴

`open Assign` 这个标签，文件里出现几十次。Myers 找最短路径时随便挑一个配上就行，结果 `WAREHOUSES = {...}` 和 `rows = []` 被配成「同一行改出来的」，两行都标红。

加上名字（`Assign:WAREHOUSES`、`Assign:rows`）之后消失。同类修复还有 `Call:print`、`FunctionDef:available`、`Attribute:get`。

还有一次更隐蔽的：一行里 4 个 token 只匹配上 1 个（就是那个 `open Assign`），但我当时的判定是「有匹配就算配对成功」，于是整行被当成「改了一点」。加了「至少 2 个 token 对上，或者把整行都覆盖」的门槛才修好。

回归测试：`test_tokens.py::test_assign_hint_carries_target`、`test_call_hint_carries_function_name`。

### 坑三：多行字符串的中间几行被当成改动

`ast.py` 开头有一段 22 行的模块 docstring。它中间的行没有 token（整个字符串是一个 `Constant` 节点），于是被当成「删了 20 行、又加了 20 行」，然后移动检测再把它们配成 `↔`。一个只改了一行代码的文件，报出来 178 行移动。

修法是：`tokenize_source` 顺带记录所有多行 `Constant` 覆盖的行号范围，这些行直接跳过不输出。

回归测试：`test_tokens.py::test_multiline_string_interior_lines_reported`。

### 坑四：`else:` 这种行也算改动

`else:`、`):`、`except:` 这些行本身不产生任何 token（`else` 不是一个 AST 节点，它只是 `If` 节点的 `orelse` 列表）。它们拿不到槽位，就被当成「删除 + 新增」，然后被移动检测配成 `↔`。同一个 1865 行文件，报出来 96 行「移动」。

修法：一行如果没有 token、也不是注释、也不是空行，就当上下文处理，不算任何变更。它的变化由所属语句块内部的变化来体现。

回归测试：`test_cli.py::CliTest::test_check_returns_zero_on_format_only` 间接覆盖。

### 坑五：注释被数了两次

注释不在语法树里，永远拿不到槽位。于是一行**完全没动过**的注释，会同时出现在旧侧（`-`）和新侧（`+`），各计一次「格式变更」。`ast.py` 里 52 条注释，报出来 105 行格式变更。

修法：加一个 `merge_comments` 后处理，按文本把两边的注释行配成一对；文本相同就不计数（算没变），文本不同才算一处格式变更。

回归测试：`test_diff.py::FormatTest::test_comment_only_change_is_format`。

### 坑六：一个性能 bug 藏在集合推导式里

1865 行的文件比较要 6.7 秒。用 `cProfile` 一看，`_evidence()` 被调了 3476 次：

```python
skip_old = {ln for ln in old_interior if ln not in _evidence(old_tokens)}
```

`_evidence(old_tokens)` 写在推导式的条件里，**每个元素都重新算一遍**。提到循环外面之后，6.7 秒变成 0.16 秒——40 倍。

回归测试：没有单独的用例，`test_diff.py` 全部用例跑完 0.26 秒本身就是回归保护（改坏了会明显变慢）。

### 这次比较顺利的部分

有一个地方我担心会很难，结果很顺：**移动检测**。原以为要做什么块级哈希、最长公共子串，实际只用「按文本配对」就够了——把删掉的行和新增的行按 `strip()` 后的文本做一对一配对，配上就是移动。整段函数挪位置这种最常见的情况，一次就对了。

代价是它只认「内容完全一致」的移动。挪的同时还改了内容，还是显示成删除 + 新增。这个限制写在 README 的「已知边界」里了。

## 八、一句话总结

**difftastic 把语法树压平成 token 序列来换取通用性，代价是在 Python 这种「缩进即语法」的语言里，它会把真实的语义变更报告成「没有变化」——我们只做 Python，把嵌套深度留在 token 里，于是那个被丢掉的信息又回来了。**
