# depmap · 2026-10-20

三秒钟看清一个 Python 项目里谁依赖谁，哪里有环，哪些文件是死代码。

---

## 一、我拆的是哪个项目

**[Graphify-Labs/graphify](https://github.com/Graphify-Labs/graphify)** — 129,279 星，Apache-2.0，Python，YC S26 项目。

它干的事一句话说清：**把任意代码库连同文档、SQL schema、配置文件、PDF 一起，转成一张可查询的知识图谱。**

**为什么选它：** 星标极高、许可证干净、核心思路（把代码结构变成图）可以用标准库 `ast` 独立实现，而且它明显背了太多东西——31 种语言、多平台安装、1,567 个未关 issue。

---

## 二、它怎么做的

它的核心是三层：

**第一层，AST 解析。** 用 tree-sitter 把 31 种语言的源码解析成语法树，提取出实体（文件、类、函数）和关系（导入、调用、继承）。

**第二层，建图。** 实体变节点，关系变边。每个节点有 ID，每条边有来源说明。

**第三层，聚类。** 用 Leiden 算法把图划分成社区，形成「模块群」的概念，方便你从宏观上看。

有三个设计决策我认为是对的：

**第一，选对了抽象层。** 大多数代码分析工具止步于「列出函数」或「画个类图」。直接建图更接近人真正想知道的东西——「改这个会影响什么」。

**第二，坚持本地确定性解析，不上向量库。** README 里明确写了 "local deterministic AST parsing, every edge explained, no vector store"。

这是个克制且正确的决定。代码结构本来就是确定的，用 embedding 去近似它，只会引入不确定性而没有收益。

**第三，每条边都能解释来源。** 不是「这两个文件相关度 0.87」，而是「因为第 42 行 import 了它」。可解释性直接决定这个结果能不能被信任。

## 三、它哪里让人难受

**痛点一：`install` 会往你的仓库里写机器绝对路径。**

> "`graphify install` (0.9.50, Windows, uv tool install) writes a **machine-absolute binary path** into the repo-tracked Codex hooks file `.codex/hooks.json`"
> —— [issue #3129](https://github.com/Graphify-Labs/graphify/issues/3129)

写进去的内容长这样：

```json
{ "command": "C:/Users/<user>/.local/bin/graphify.EXE hook-check" }
```

关键问题在于 **`.codex/hooks.json` 是被 git 跟踪的共享文件**。这个路径换台机器就废了，而且会污染别人的 checkout。

一个只读的分析工具，为什么要往你的仓库里写东西？

**痛点二：CLI 主函数 2,560 行。**

> "`graphify/cli.py` is 2,777 lines; `dispatch_command` starts at line 215 and runs to the end — roughly **2,560 lines in a single function**, an `if cmd == … / elif cmd == …` chain."
> —— [issue #2474](https://github.com/Graphify-Labs/graphify/issues/2474)

一个函数里塞 2,560 行 if/elif，意味着每加一个子命令都在给这坨东西继续加压。这是功能蔓延的直接证据。

**痛点三：节点 ID 撞车，边会串台。**

> "`graphify.extract` derives every node ID from `path.stem` (the extension-less basename). Two source files that share a basename therefore collapse into a single graph node — regardless of language or directory. This **silently cross-wires unrelated code**."
> —— [issue #1829](https://github.com/Graphify-Labs/graphify/issues/1829)

`a/layout.py` 和 `b/layout.ts` 会变成同一个节点，它们的边互相串。

**这个 bug 比崩溃危险得多**——不报错，只是悄悄给你一张错的图。你拿着错的图去改代码，后果可想而知。

**痛点四：同样输入，不同输出。**

[#1667](https://github.com/Graphify-Labs/graphify/issues/1667) 报告相同语料跑两次，社区划分结果不一致。对结构分析工具来说，不可复现的输出基本等于不可用。

## 四、我们做了什么

**定位一句话：一个只读的命令行工具，只做 Python 代码结构这一层，输出确定、可接 CI。**

### 砍掉的

| 砍掉 | 为什么 |
|---|---|
| 多语言 AST（tree-sitter） | 一个语言做到准，比三十个语言做到半准有用。Python 标准库 `ast` 就够，且零依赖 |
| 文档 / SQL / PDF 摄入 | 那是「知识图谱」，我们只做「代码结构」。混在一起会让输出无法验证 |
| MCP / agent 集成 / install | #3129 的根源。只读工具不该往你仓库写任何东西 |
| 语义层 / embedding | 代码结构是确定的，用近似只会引入噪声 |
| 社区划分（Leiden） | #1667 的不确定性来源。模块依赖图不聚类也有用 |

### 保留的

确定性 AST 解析、每条边可追溯、多种输出格式。

### 自己加的三条

**1. 节点 ID 用完整相对路径。** 直接对应 #1829。`a/layout.py` 和 `b/layout.py` 永远是两个节点。

**2. 循环依赖检测 + CI 退出码。** `--check` 有环就返回 1，能直接挂进 CI。原版是给你一张图让你自己看。

**3. 解析失败必须上报。** 有语法错误的文件会出现在 `unparsed` 列表里，不会静默消失。

### 它是怎么工作的

**第一步：把文件变成模块名。** `app/api/users.py` → `app.api.users`。`app/__init__.py` → `app`。

**第二步：把 import 语句解析成边。** 这里有个细节——相对导入要正确解析：

```python
# 文件 pkg/sub/mod.py 里
from . import helper      # → pkg.sub.helper
from .helper import x     # → pkg.sub.helper
from ..core import y      # → pkg.core
```

`from .` 的层级要往上退到正确的包，这是最容易写错的地方。

**第三步：找环。** 用 DFS 遍历，遇到「指向自己栈上祖先」的边就说明有环，把栈上那一段取出来就是环路。

**第四步：找孤立和入口。** 没有任何边连着的模块 = 死代码；只被依赖、不依赖别人的 = 入口模块。

## 五、和原版差在哪

| 维度 | graphify | depmap |
|---|---|---|
| 安装 | 需要 install 子命令 | 无。下载一个 `.py` |
| 依赖 | tree-sitter 等 | 标准库，零依赖 |
| 语言覆盖 | 31 种 | 仅 Python |
| 摄入范围 | 代码 + 文档 + SQL + PDF | 仅代码 |
| 改你的仓库 | 会写 `.codex/hooks.json` | 只读，不写任何文件 |
| 节点 ID | 文件名（会撞车） | 完整相对路径 |
| 循环依赖 | 不给结论 | 直接列出，可接 CI |
| 确定性 | 社区划分不确定 | 完全确定 |
| 代码量 | 31 MB 仓库 | 约 380 行 |

## 六、怎么用

```bash
git clone https://github.com/z15346183030/depmap && cd depmap

python depmap.py .                    # 摘要
python depmap.py . --format mermaid   # 粘进 GitHub/Notion 就能看图
python depmap.py . --check            # 有环就退出码 1，接 CI
```

实测 CPython 标准库两个真实包：

| 包 | 模块数 | 内部依赖 | 循环依赖 |
|---|---|---|---|
| `asyncio` | 33 | 129 | 1 |
| `email` | 29 | 74 | 11 |

## 七、开发中踩的坑（这个最值得说）

第一版在 `asyncio` 上报了 **7 处循环依赖**。看起来很像真的。

我逐条核对，发现 **6 个是假的**。

**误报一：扫包目录时，绝对导入被当成内部模块。**

`asyncio/events.py` 里有一句 `import subprocess`——指的是标准库的 `subprocess`。

但我以 `asyncio/` 为根扫描，同目录正好有个 `subprocess.py`，于是被解析成了内部依赖。

**修法**：如果根目录本身是包（有 `__init__.py`），模块名统一加包名前缀（`asyncio.events`）。这样绝对导入就再也匹配不上同目录文件了。

**误报二：`from . import x` 把包本身也算成了依赖。**

`asyncio/base_events.py` 里全是 `from . import events` 这类语句。我最初把「包」也放进了候选目标，结果每个子模块都连回 `asyncio/__init__.py`，凭空造出：

```
asyncio → asyncio.base_events → asyncio
```

**修法**：相对导入只依赖具体的子模块，不依赖包本身。

**误报三：不存在的子模块被兜底成整个包。**

`from . import staggered` 如果 `staggered.py` 不存在，我的「逐级向上找」逻辑会退回 `asyncio`——又一条假边。

**修法**：模糊匹配只对绝对导入开启。相对导入的基准是确定的，不该猜。

修完这三处，`asyncio` 的环从 7 处降到 1 处。剩下那处是 `tasks ↔ timeouts`，我 grep 核对过：

- `asyncio/tasks.py:29` → `from . import timeouts`
- `asyncio/timeouts.py:8` → `from . import tasks`

**是真的。**

三个误报都写了回归测试锁住。

## 八、这件事的教训

**分析工具报 7 个问题、其中 6 个是假的，比一个都不报更糟。**

因为你会开始怀疑它报的第 7 个——而第 7 个恰恰是真的。信任一旦破了，工具就废了。

所以做分析类工具，「不漏报」是次要的，**「不误报」才是第一优先级**。

---

## 九、一句话总结

graphify 想当你的知识图谱大脑，depmap 只想在你动代码之前告诉你「这几个文件绕成环了」。

**小而准，胜过全而糊。**
