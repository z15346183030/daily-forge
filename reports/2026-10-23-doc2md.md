# doc2md · 2026-10-23

## 一、我拆的是哪个项目

[microsoft/markitdown](https://github.com/microsoft/markitdown)，191,666 星，MIT 许可证，Python。

一句话定位：**把任何文件转成适合喂给大模型的 Markdown**。

选它的理由有三条。

第一，它解决的问题是真的。你手上有 Word 报告、Excel 台账、PPT 汇报，想让模型读，
第一步永远是「先转成文本」。这一步看起来简单，实际上每个人都写过一遍，而且都写得不太对。

第二，它的痛点是结构性的，不是 bug。它的 README 承诺「any file」，
于是不得不把 docx、xlsx、pptx、pdf、epub、图片、音频、YouTube、ZIP、Outlook 邮件、
维基百科全塞进去——我数了一下 `converters/` 目录，**24 个转换器文件**。
每多一个格式，就多一组依赖、多一条失败路径。而绝大多数人只需要其中两三个。

第三，也是最关键的：它的默认依赖里有一个 `magika`，那是一个用 ONNX 模型猜文件类型的库。
**为了知道一个 `.docx` 是 docx，它要加载一个神经网络。** 这个设计选择暴露了整个项目的取向——
宁可重，也要全。这正好是我们能切进去的地方。

许可证干净（MIT），90 天内还有提交（2026-10-22），门槛全过。

## 二、它怎么做的

### 整体结构

```
用户调用 convert(path)
        │
        ▼
  猜类型（三路兜底）
  ├─ 扩展名
  ├─ MIME
  └─ magika 读前 2KB 字节 → ONNX 模型 → 类型标签
        │
        ▼
  按优先级遍历 24 个转换器，谁 accepts() 返回 true 谁上
  ├─ ZipConverter        （解压再递归）
  ├─ PdfConverter        （pdfminer + pdfplumber）
  ├─ DocxConverter       （mammoth → HTML → markdownify）
  ├─ XlsxConverter       （pandas + openpyxl → DataFrame → 表格）
  ├─ PptxConverter       （python-pptx → 遍历 shape）
  ├─ AudioConverter      （SpeechRecognition）
  ├─ YouTubeConverter    （抓字幕）
  └─ ... 还有 17 个
        │
        ▼
  DocumentConverterResult(markdown, title)
```

这个架构本身很漂亮。`accepts()` + 优先级 = 加格式不用改主流程，
24 个转换器互不干扰，测试也好写。**它做对的地方就在这里：把「格式」抽象成了可插拔的单元。**

但漂亮是有代价的。为了支撑这个抽象，它必须接受「每个转换器带自己的依赖」，
而依赖是全局的——你装了 markitdown，就装了 pandas、onnxruntime、pdfplumber、Pillow、
lxml、python-pptx、mammoth……不管你只用不用得到。

### docx 那条路特别值得说

markitdown 转 docx 的路径是：

```
report.docx ──mammoth──▶ HTML ──markdownify──▶ Markdown
```

为什么绕这一圈？因为 mammoth 已经能把 docx 转成「语义化的 HTML」，
而 HTML 转 Markdown 是一个成熟问题。两步都是现成的库，拼起来最快。

代价是：**中间那层 HTML 会丢信息**。HTML 的表格只有 `<tr>/<td>`，
没有「表头」这个概念；所以 markdownify 转回 Markdown 时，只能把第一行当表头，
或者干脆造一个空表头。我实测了同一份文件，原版输出的表格长这样：

```markdown
|  |  |  |
| --- | --- | --- |
| 指标 | 上季度 | 本季度 |
| 交付周期 | 14 天 | 9 天 |
```

表头是三个空格子，真正的表头被降级成了第一行数据。表格在视觉上还是表格，
但语义上「这一列是什么意思」这条信息没了——对要喂给模型的东西来说，这是实质损失。

而我们直接读 `word/document.xml`，`w:tbl` 的第一个 `w:tr` 天然就是表头，
不需要猜，也不会丢。

## 三、它哪里让人难受

### 1. 为了猜类型，装了一个 ONNX 运行时

[#1234 [Feature Request] Magika Dependency Optional](https://github.com/microsoft/markitdown/issues/1234)（open，12 条评论）

> "Would it be possible to make the Magika dependency optional (i.e., pulled in as an extra)?
> I'm trying to use MarkItDown in the browser via Pyodide and Magika's dependency on ONNX is causing trouble."
>
> "I tested with a forked repo where I removed `self._magika.identify_stream(file_stream)`
> from `_get_stream_info_guesses()` and I was able to convert PDFs in the browser."

注意最后一句：**用户自己删掉一行，功能就正常了**。这说明 magika 对大多数场景不是必需的，
它只是「更聪明」。但它在 `dependencies` 里，不在 `optional-dependencies` 里，
于是每个只想转 docx 的人都要为它付安装成本。

我实测了一下这个成本：`pip install markitdown[docx,xlsx,pptx,pdf]` 装完，
`site-packages` 是 **271 MB，38 个包**。其中 onnxruntime 一家就占了大头。

更黑色幽默的是，在这台机器上装完之后，`import onnxruntime` 直接**段错误退出**（exit 139），
连 `import markitdown` 都过不去。我最后是写了一个假的 `magika` 模块顶上去，才跑通对比测试。
这不是 markitdown 的 bug，是「重依赖」这件事本身的代价：依赖越多，
在你的机器上跑不起来的方式就越多。

### 2. 缺一个字段就整个文件崩

[#1282 DocxConverter threw KeyError with message: 'w:ilvl'](https://github.com/microsoft/markitdown/issues/1282)（open，14 条评论）

> `markitdown data/demo.docx > document.md --keep-data-uris`
> `FileConversionException: File conversion failed after 1 attempts`

`w:ilvl` 是 Word 列表的「层级」属性，0 是第一层，1 是第二层。
在 OOXML 规范里，这个属性是**可以省略的**，省略即第 0 层。
但 WPS、在线文档、脚本生成的 docx 经常不写它——于是整条链路在某处按 key 取值，KeyError 冒到顶层。

用户看到的是一整页 Python 堆栈，而不是「这份文档的列表格式不规范，我按第一层处理了」。

我按 issue 的描述构造了一份「只有 numId、没有 ilvl」的 docx 去复现，
用 mammoth 1.13 跑下来这次没崩——说明触发条件比「缺 ilvl」更具体，可能还跟编号定义的层级表有关。
但这个 issue 存在本身就说明了问题：**容错应该发生在读 XML 的那一层，而不是靠上游库碰巧修好。**
所以我们的实现里，`ilvl` 一律 `get(..., "0")`，并且有一条专门的回归测试钉住它。

### 3. PDF 表格：看起来转了，其实错了

[#293 Tables in pdf files are not converted properly](https://github.com/microsoft/markitdown/issues/293)（open，10 条评论）

> "I converted a pdf-file with lots of table to markdown. I had expected that `markitdown`
> would handle tables gracefully."

用户贴的是一张寄存器表，期望得到规整的三列表格，实际得到的是一堆错位的文字。
同类还有 [#41 Preserve tables, titles (structure) of PDF documents](https://github.com/microsoft/markitdown/issues/41)（11 条评论）。

这里我要说一句可能不讨喜的话：**PDF 表格做不好是正常的**。
PDF 里根本没有「表格」这个对象，只有一堆绝对坐标的文字块。
从坐标反推表格是启发式问题，做不好很正常。

真正的错误不是「做不好」，而是**默认输出一份看起来像表格、实际上列对不上的东西**。
这种输出喂给模型比不喂更糟——模型不会怀疑输入，它会拿着错位的列去编一个自洽的解释。

### 4. 边界越扩越模糊

- [#12 LLM Integration](https://github.com/microsoft/markitdown/issues/12)（17 条评论）：接大模型，把图表转成表格
- [#114 图片无法转换](https://github.com/microsoft/markitdown/issues/114)（14 条评论）：要 OCR
- [#2106 How to use it in Windows 11？](https://github.com/microsoft/markitdown/issues/2106)（10 条评论）：卡在 `source .venv/bin/activate` 这条 Linux 命令上

三个需求都合理，但方向完全不同：接大模型要网络和密钥，OCR 要模型权重，Windows 支持要平台适配层。
一个工具同时做这些，最后就是安装体积、配置项、失败模式一起膨胀。
`#2106` 那条尤其说明问题——**用户连第一步都没走通**，而 README 里写的是 Linux 的命令。

## 四、我们做了什么

### 一句话定位

**把 Office 文档转成 Markdown，只用 Python 标准库，装完就是零依赖。**

### 取舍

| 决定 | 内容 | 为什么 |
|---|---|---|
| 砍 | PDF | 标准库做不出正确的表格。宁可报错说「用 pdftotext」，也不给一份错位的表格 |
| 砍 | 音频转写、YouTube 字幕、EPUB、ZIP、Outlook | 都需要外部服务或额外依赖，和零依赖互斥 |
| 砍 | Azure 文档智能、LLM 图片理解 | 要账号、要密钥、要联网，违反零配置 |
| 砍 | magika 内容嗅探 | 扩展名已经够了。猜错类型时，报错比猜更有用 |
| 砍 | 24 个转换器的继承体系 | 只有 6 种格式，一个 dict 分发就够 |
| 留 | docx 的标题、列表、表格、链接 | 这四样是文档结构的骨架，少一个转出来就没法读 |
| 留 | xlsx 的日期还原 | Excel 把日期存成 45000 这种序列号，不还原就是天书 |
| 留 | pptx 的备注 | 备注往往是讲稿，信息量比幻灯片上的短句大 |
| 加 | 缺 `ilvl` 按第 0 层处理 | 直接对应 #1282，有默认值的属性缺失不该让文件失败 |
| 加 | 真实的有序列表序号 | 原版输出全写 `1.`，能渲染但源码是错的 |
| 加 | 没有占位符时按字号挑标题 | 设计感强的 deck 全是普通文本框，硬套项目符号会把标题变成列表项 |
| 加 | 页码域过滤 | `1/3` 这种页码混进正文只是噪音 |
| 加 | 中文样式名识别 | `标题 1` 和 `Heading 1` 都得认 |

### 核心怎么工作的

整个工具只做一件事：**把 OOXML 里的三种结构（文本、层级、表格）读出来，再按 Markdown 的语法拼回去。**

OOXML 文件本质是一个 zip：

```
report.docx
├── [Content_Types].xml
├── word/
│   ├── document.xml      ← 正文都在这里
│   ├── styles.xml        ← styleId → 样式名（"Heading1" → "heading 1"）
│   ├── numbering.xml     ← numId → 各层级的编号格式（bullet / decimal）
│   └── _rels/document.xml.rels  ← rId → 超链接地址、图片路径
```

以一份「季度复盘」为例，`document.xml` 里一段标题长这样：

```xml
<w:p>
  <w:pPr><w:pStyle w:val="Heading1"/></w:pPr>
  <w:r><w:rPr><w:b/></w:rPr><w:t>季度复盘</w:t></w:r>
</w:p>
```

我们要回答三个问题：

1. **这段是几级标题？** 先看 `w:pPr/w:outlineLvl`（0 表示一级，最可靠）；
   没有再拿 `w:pStyle` 的值去 `styles.xml` 查样式名，用正则 `^(heading|标题)\s*([1-9])$` 匹配。
   两条都不通，就当正文。
2. **这段是不是列表？第几层？** 看 `w:numPr` 里有没有 `numId`。
   `numId=0` 表示「没有编号」；有的话再查 `numbering.xml`：
   `numId → abstractNumId → lvl[ilvl] → numFmt`，`numFmt` 是 `bullet` 就输出 `-`，
   是 `decimal` 就输出递增的数字。**`ilvl` 不存在时按 0 处理，这就是 #1282 的那个坑。**
3. **这段有什么格式？** 遍历 `w:r`，看 `rPr` 里有没有 `w:b` / `w:i` / `w:strike`，
   包上 `**` / `*` / `~~`。`w:hyperlink` 则拿 `r:id` 去 rels 里换出真实 URL。

表格更直接：`w:tbl → w:tr → w:tc`，每个 `w:tc` 里所有段落拼成一行，
`gridSpan` 有几格就补几个空格子。第一行 `w:tr` 就是表头——**不需要猜，因为 XML 里它就是第一行**。

xlsx 多一步日期还原。Excel 把 `2023-03-15` 存成整数 `45000`，
所以要看单元格的 `s` 属性（样式索引）指向的 `numFmtId`，
如果是日期格式（内置 14–22、45–47，或者自定义格式里带 `y/d/h/s`），
就用 `1899-12-30 + 45000 天` 算回真实日期。不做这一步，输出就是一堆 `45000`。

pptx 的坑在顺序。幻灯片文件叫 `slide1.xml`、`slide2.xml`……`slide10.xml`，
按文件名排序，第 10 页会插到第 2 页前面。正确做法是读 `presentation.xml` 里的 `sldIdLst`，
拿 `r:id` 去 rels 换出真实路径——**顺序以放映顺序为准，不以文件名为准**。

### 实测数字

| 场景 | doc2md | markitdown |
|---|---|---|
| xlsx，2 万行 × 8 列（16 万单元格） | **1.33 s** | 19.0 s |
| docx，3000 段 + 200 个表格 | **0.06 s** | 1.84 s |
| 冷启动 import | **0.30 s**（解释器本身 0.18 s） | 1.95 s |
| 安装体积 | **0** | 271 MB / 38 个包 |

xlsx 差 14 倍，docx 差 33 倍。差距不在算法，在路径：
原版把 xlsx 建成 pandas DataFrame 再转 Markdown，中间要构造几十万个 Python 对象；
我们只把 XML 里的 `<v>` 取出来拼字符串，中间没有模型层。

```bash
与其给你一份看起来对、实际错位的表格，不如不做。需要 PDF 就用 pdftotext。
```

## 七、开发中踩的坑

**坑一：共享字符串读不出来，整张表变成空格子。**

第一版跑 `examples/table.xlsx`，输出是 `|  |  |` 一片空白。
原因是我的 `_text_of()` 只认 `w:t` 和 `a:t` 两种文本节点，而 xlsx 的文本节点是 `x:t`。
三种格式的命名空间不同，但本地名都是 `t`，所以改成按本地名判断：

```python
node.tag.rsplit("}", 1)[-1] == "t"
```

一处代码三种格式通用。回归测试：`test_shared_strings_and_numbers`。

**坑二：日期样式读不到，`2023-03-15` 显示成 `45000`。**

`styles.xml` 的结构是 `styleSheet > numFmts > numFmt`，
我用了 `root.findall(X + "numFmt")`——`findall` 只找直接子节点，而 `numFmt` 在 `numFmts` 里面。
改成 `root.iter(X + "numFmt")` 就好了。回归测试：`test_date_serial_becomes_readable_date`。

**坑三：列表项之间被空了一行，有序列表断了。**

Markdown 里相邻两个列表项之间如果空一行，会被当成两个独立的松散列表，
有的渲染器还会重新从 1 开始编号。我的 `clean_blocks()` 给所有块之间都加了空行，
于是 `1. 步骤一` 和 `2. 步骤二` 被拆散了。修法是让 `clean_blocks()` 认一下：
如果当前块和上一块的最后一行都是列表行，就贴在一起。回归测试：`test_ordered_and_bullet_lists_with_levels`。

**坑四：有序列表的序号全是 1。**

一开始为了省事，所有有序列表项都输出 `1.`——CommonMark 会自动重编号，看起来没问题。
但用户读的是**源码**（要喂给模型），一列 `1. 1. 1.` 是错的信息。
改成按 `(numId, ilvl)` 记计数器，逐个递增。

**坑五：设计感强的 PPT，标题全变成了项目符号。**

拿一份真实的内部汇报 PPT 试，输出是 `- 有IT问题 找HiIT`、`- 2022-07`、`- 流程IT与数据管理部`。
原因是这份 PPT 整页都是**普通文本框**，一个占位符都没有（`<p:ph>` 为空），
我的代码就把每一段都当成了正文项目符号。

修法两条：只有真的带 `a:buChar` / `a:buAutoNum` 的段落才输出 `-`；
标题按**字号**挑——一页里字号最大的那个文本框就是标题。
回归测试：`test_largest_font_becomes_title_when_no_placeholder`。

**坑六：页码 `1/3` 混进了正文。**

幻灯片右下角的页码是个 `a:fld` 域，不是普通文本。跳过 `type="slidenum"` 的域，
以及 `ph type` 为 `sldNum` / `ftr` / `hdr` 的占位符。

**坑七（这次没踩，但差点踩）：`examples/` 里的样本文件让测试变得不可靠。**

一开始想直接放三个二进制样本进仓库。后来改成 `examples/make_examples.py` 现场生成，
测试用的 docx/xlsx/pptx 也是 `tests/fixtures.py` 用 `zipfile` 拼出来的——
每个用例看到的结构都是可控的，改一行 XML 就能构造一个边界情况，
也不用担心二进制文件在 git 里产生无法 review 的 diff。

## 八、一句话总结

markitdown 想解决的问题是「什么文件都能转」，doc2md 只回答「Office 文档怎么转对」——
砍掉 18 种格式和一个神经网络之后，快了 14 倍，装了 0 个包，表格的表头终于还是表头。
