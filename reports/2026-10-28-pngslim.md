# pngslim · 2026-10-28

## 一、我拆的是哪个项目

[oxipng/oxipng](https://github.com/oxipng/oxipng) — 4,302 星，MIT，Rust，最新版本 v10.2.1，十天前还有提交。

一句话定位：**把 PNG 压到不能再小，像素一个不变**。

为什么选它。我本来想找「配置太多、抱怨太重」的项目，翻了一圈 GitHub Trending，
当天全是 agent / skill 仓库，没有可拆的算法内核，于是回到搜索接口按星标翻。
oxipng 满足全部硬门槛（4,302 星、MIT、Rust、十天内提交），
而且它有一个我很感兴趣的特征：**它的核心算法极其朴素，但外围的参数极其复杂**。

朴素到什么程度？整个优化过程就是「生成一堆候选图像，每个候选压一遍，留最小的那个」。
复杂到什么程度？38 个命令行参数，其中 `-o` 一条旋钮有 8 档，
每一档展开是一串没人看得懂的数字（`-f 0,1,6,7,8,9 --brute-level 1 --brute-lines 4`）。

这种「内核简单、旋钮复杂」的项目，正是能做精简版的类型。

## 二、它怎么做的

PNG 的像素数据是按行存的，每行开头有一个字节，说明这行用了哪种**预测**：

```
原始像素行:   [10, 12, 15, 18, 22]
滤波 1 (sub): [10,  2,  3,  3,  4]   存「和左边像素的差」
滤波 2 (up):  [10,  1,  2,  2,  3]   存「和上一行同位置的差」
滤波 4 (paeth): 用左、上、左上三个值猜一个，存差值
```

差值的数值小、重复多，后面那层 deflate 就能压得更狠。所以「怎么滤波」和「怎么 deflate」
是两件可以独立选择的事，最终文件大小取决于这个组合。

oxipng 的架构就是把这两件事拆成两条轴：

```
                ┌─────────────────────────────────────────┐
   读文件  ───► │ PngData::from_slice                       │
                │   ├─ 解析 chunk（IHDR/PLTE/tRNS/IDAT/...）│
                │   └─ 解压 IDAT，逐行反滤波 → 原始像素      │
                └───────────────┬─────────────────────────┘
                                │
                ┌───────────────▼─────────────────────────┐
                │ src/reduction/   「像素怎么表示」          │
                │   bit_depth.rs  16 位 → 8 位              │
                │   color.rs      RGBA → RGB（alpha 全 255）│
                │   palette.rs    真彩色 → 调色板            │
                │   alpha.rs      透明像素的颜色随便改       │
                │   interlace.rs  隔行 ↔ 不隔行              │
                └───────────────┬─────────────────────────┘
                                │  每个 reduction 产生一个新候选
                ┌───────────────▼─────────────────────────┐
                │ src/evaluate.rs  Evaluator                │
                │   每个候选 × 每种滤波策略                  │
                │      → 滤波 → deflate → 算最终文件大小     │
                │      → 比当前最优大就立刻放弃              │
                │   全部结果按 (大小, 数据长度, 策略) 排序    │
                └───────────────┬─────────────────────────┘
                                │
                ┌───────────────▼─────────────────────────┐
                │ src/filters/   src/deflate/               │
                │   9 种滤波策略（含一个真压缩比大小的 Brute）│
                │   libdeflate（等级 0-12）或 Zopfli         │
                └───────────────┬─────────────────────────┘
                                │
                ┌───────────────▼─────────────────────────┐
                │ 拼回 PNG：新 IDAT + 原样的 aux chunk      │
                └─────────────────────────────────────────┘
```

三个值得记下来的设计：

**候选之间互相竞争，而不是流水线。** `src/evaluate.rs` 里的 `Evaluator` 是个收集器：
每个候选在自己的线程里跑「滤波 → 压缩 → 算大小」，结果回到主线程按大小排序取最小。
压缩到一半发现已经比当前最优大了，就直接放弃——`best_candidate_size` 是一个原子最小值，
所有线程都能读。这一条是「暴力试」能跑得动的原因。

**滤波策略不止标准那五种。** 除了 none/sub/up/avg/paeth，还有 MinSum、Entropy、Bigrams、
BigEnt，以及一个叫 Brute 的：把若干行当成一块，每种滤波都真的压一遍，谁小用谁。
`-o 4` 用的是 `-f 0,1,6,7,8,9`——**标准滤波反而不在列表里**。

**只重写需要重写的部分。** `aux_chunks` 原样搬运，`--strip` 是可选项不是默认，
`-p` 保留时间戳和权限。这一点它做得很克制。

## 三、它哪里让人难受

### 一、`-o` 是一条看不见底的旋钮

`--help` 里 38 个参数，`-o` 有 8 档，帮助文本长这样：

```
0   => --zc 5  -f 0,5         --fast
2   => --zc 11 -f 0,1,6,7     --fast
4   => --zc 12 -f 0,1,6,7,8,9 --fast --brute-level 1 --brute-lines 4
6   => --zc 12 -f 0-9                --brute-level 5 --brute-lines 8
max => (stable alias for the maximum level)
```

`zc` 是压缩器等级，`f` 是滤波策略编号，`brute-level` / `brute-lines` 是 Brute 策略的两个参数。
帮助文本对后两个的说明是：

> Set the libdeflate compression level to use with the Brute filter strategy.
> **Sane values are 1-5. Higher values are not necessarily better.**

一个工具自己承认「更大的数不一定更好」，等于承认这个旋钮没法靠推理调，只能试。

issue [#757](https://github.com/oxipng/oxipng/issues/757)（2025 年 12 月开的，14 条回复，至今没关）
第一句话就是：

> How does this compare to optipng?

一个用了十年、四万多人 star 的工具，用户还在问「我到底该用哪个」，这本身就是答案。

我实测了这条旋钮到底值多少（同一批 72 个文件，8 核）：

| 等级 | 输出 | 比上一档省 | 耗时 |
|---|---|---|---|
| `-o 2` | 11,123,331 B | — | 11.3 s |
| `-o 4` | 11,061,030 B | 0.56% | 22.0 s |
| `-o max` | 11,050,122 B | 0.10% | 137.7 s |

从 4 档到 max，时间涨 6.3 倍，多省 0.1%。**这条旋钮的后半段基本是在拿电费换小数点后一位。**

### 二、它默认会改你的图像头

`-o 4` 在 69 个文件里改掉了 8 个的 IHDR：6 个把 32 位 RGBA 降成 24 位 RGB（因为 alpha 全是 255），
2 个把真彩色换成调色板。这是 `src/reduction/` 在干活，默认开启。

问题不在于「对不对」——它做得对。问题在于这个转换对下游有影响：
按「每像素 4 字节」算内存的代码、按色彩类型分支的着色器、把 PNG 当纹理上传的引擎，
都可能因为这个静默的变化出问题。issue [#790](https://github.com/oxipng/oxipng/issues/790)
就是在问怎么**阻止**它转成调色板：

> Way to force greyscale instead of indexed?

而在我们这批文件上，全部 reduction 加起来只值 45,412 字节：
`-o 4` 是 11,061,030 B，加上 `--nx` 关掉所有 reduction 是 11,106,442 B——**0.36%**。

为了 0.36%，默认改变了 12% 文件的编码结构。这笔账不太划算。

### 三、跑完你不知道整体省了多少

issue [#678](https://github.com/oxipng/oxipng/issues/678)（34 条回复）：

> the per-file statistics of oxipng makes for quite a cluttered window and rather hard to see
> how much of an overall improvement it had. `-q` stops the flood of file paths, but doesn't
> display anything at all.

它的输出是「一个文件一行」，`-q` 是「一行都不给」。中间那档「给我一个总数」长期不存在。
后来加了 `--json` 才算有个出口——但你得自己 `jq` 一下。

关闭这条 issue 的理由是「要改 API 才能拿到输入输出大小」。
一个「汇总」功能，被内部数据结构的形状卡了三年。

### 四、中断了就得从头再来

issue [#549](https://github.com/oxipng/oxipng/issues/549)：

> I have run oxipng at my home folder yesterday, but it has take forever and I have abort it.
> Today I started it again, but it starts from the beginning. Because I have absolute no idea
> where it has stop I can not continue without starting from scratch.

维护者的回复很实在：这是脚本该干的事，不该进核心。这个判断未必错，
但它暴露了一件事——**工具没有「这个文件已经压过了」的概念**。
没有这个概念，就没法幂等，也就没法安全地重跑。

### 五、超时旋钮基本没用

`--timeout` 的帮助文本自己写着：

> Note that this does not cut short any operations that are already in progress,
> so it is currently of limited effectiveness for large files with high compression levels.

大文件 + 高压缩等级，正好是最需要超时的场景，而它恰好在那个场景失效。

## 四、我们做了什么

一句话：**只做「重新滤波 + 重新压缩」这一件事，绝不碰图像头，一个文件跑完，不给任何调优旋钮。**

砍掉的和留下的：

| 砍掉 | 为什么 |
|---|---|
| 全部 reduction（位深 / 色彩类型 / 调色板 / 透明 / 隔行） | 实测只值 0.36%，却要改 IHDR。不改头，就能给出「像素必然相同」的结构性保证 |
| `-o 0..6` 七档预设 | 换成「便宜压缩器给所有候选打分，只对冠军用贵的压缩器」，不需要人调 |
| Brute / MinSum / Entropy / Bigrams / BigEnt | 保留逐行自适应（none/sub/up/avg 里选），实测和逐块暴力差 0.08% |
| `--strip` `--alpha` `--out` `--stdout` `--preserve` `--threads` | 默认不动元数据、不动权限，输出就是原地替换 |
| Zopfli | 需要额外依赖，而这个工具的意义就是零依赖 |
| APNG 帧优化 | 帧是独立 chunk，只压第一帧会改动画。明确跳过并说明原因 |

| 加上 | 为什么 |
|---|---|
| `--check` | 退出码 1 表示「还有能省的地方」，可以直接当 CI 闸门 |
| `--explain` | 列出每个候选滤波的字节数和耗时，回答「这个文件为什么这么大」 |
| 幂等 | 第二次跑同一个目录，输出字节完全不变，报 0 B |
| 写盘前自检 | 每次把结果解回来逐行比对，不一致就不写 |

核心算法分四步：

1. 六个候选（none / sub / up / avg / paeth / 逐行自适应）各自把整幅图滤波一遍
2. 每个候选的结果用 **zlib level 1** 压一下，拿字节数当分数
3. 分数最低的那个，用 zlib level 9 正式压，同时试 `Z_DEFAULT` 和 `Z_FILTERED` 两种策略
4. 挑最小的一份写出去，写完解回来逐行比对

第 2 步是整个设计的支点。用便宜压缩器当裁判，实测在 6 个文件上
**level 1 的排名和 level 9 的排名完全一致**，而 level 1 只花 level 9 的 1/20 时间。
在 8 个文件的子集上，「level 1 打分」和「每个候选都跑 level 9」的结果**一个字节都不差**
（1,455,800 B），耗时 6.5 秒 vs 18.2 秒。

为什么必须「试一遍再挑」？因为选错滤波的代价是 30%。实测最极端的一个文件
（1200×1200 二维码，5.76 MB 原始数据）：

| 滤波 | 输出 |
|---|---|
| none | **98,572 B** |
| adaptive | 116,206 B |
| paeth | 121,002 B |
| up | 121,826 B |
| sub | 123,010 B |
| avg | 129,224 B |

二维码是大片相同字节，本来就是最好的 deflate 输入，一差分反而把「一片 0」打散成噪声。
照片和渐变正好相反，`avg` / `paeth` 能省 20% 以上。**同一套逻辑没法通吃，只能试。**

## 五、和原版差在哪

| 维度 | oxipng `-o 4` | pngslim |
|---|---|---|
| 输出体积（72 文件） | 11,061,030 B（-11.5%） | 11,642,134 B（-6.8%） |
| 耗时（8 核） | 22.0 s | 63.3 s |
| 安装 | 下载二进制或 `cargo install` | 无，一个 .py 文件 |
| 依赖 | libdeflate / Zopfli | Python 标准库 |
| 是否改 IHDR | 69 个文件里改了 8 个 | 一个都不改 |
| 元数据 | 默认保留，`--strip` 可删 | 永远保留，没这个开关 |
| 参数个数 | 38 | 9 |
| 调优旋钮 | `-o 0..6/max` + 5 个底层参数 | 无 |
| 默认输出 | 每个文件一行 | 汇总 + 最大收益前五 |
| 二次运行 | 重新压一遍 | 字节不变，报 0 B |
| CI 闸门 | 无 | `--check` |
| 候选解释 | `-vvv` 的 trace 日志 | `--explain` 一张表 |

体积和速度两项都是原版赢，这是实话，而且原因很干净——**差距全在 deflate 引擎**。

拿一张图，用 `avg` 滤波一次，然后把**同一份字节流**交给不同的编码器：

| 编码器 | 同一份滤波数据的输出 |
|---|---|
| zlib level 9（本工具） | 1,332,570 B |
| libdeflate level 9 | 1,302,786 B |
| libdeflate level 12（oxipng `-o 4`） | 1,235,908 B |

7.3%，纯粹是熵编码器的实力差距，跟滤波策略、搜索方式、代码写得好不好都没关系。
Python 标准库里只有 zlib，这部分追不回来。

所以这个工具的定位不是「更好的 oxipng」，而是「**装不了二进制的地方的 oxipng**」：
锁死的 CI runner、没有 cargo 的 Alpine 镜像、别人笔记本上一个临时脚本。
拷一个文件过去，拿到三分之二的收益。

## 七、开发中踩的坑

**坑一：抽样选滤波，损失了 1.5%。**
第一版为了快，从图里**均匀散点抽 96 行**，滤波后压一下给六个策略打分。
结果在 8 个文件的子集上只做到 1,478,140 B，而全量评估是 1,455,800 B——差了 22,340 B（1.5%）。
原因很直白：散点抽样把第 3 行和第 51 行拼在一起，**破坏了「上一行」这个关系**，
而 up / paeth 两个滤波的收益全建立在垂直相关性上。抽样把它们系统性判低了。

改法：抽**连续的三段行带**（各 32 行），保住段内的垂直连续性。同一个子集立刻回到 1,456,586 B，
离全量只差 786 B（0.05%）。

**坑二：最后发现根本不用抽样。**
既然 level 1 压缩很便宜，为什么不直接给整幅图打分？改成「六个候选各自全量滤波 + level 1 压缩」之后，
子集结果 1,455,800 B——**和全量 level 9 评估一个字节都不差**，耗时 6.5 秒（全量是 18.2 秒）。
抽样那套启发式被整个删掉了，代码短了，结果还更准。回归用例：
`test_outcome_records_the_winning_filter`（冠军必须出现在候选列表里，且确实更小）。

**坑三：SWAR 的进位会串道。**
把一行当成一个大整数、每字节一个 lane 来加减，速度从 7 MB/s 提到 70 MB/s。
但普通的 `+` / `-` 会让低字节的进位污染高字节。正确写法是：

```
减法: ((x | 0x80..) - (y & 0x7f..)) ^ ((x ^ ~y) & 0x80..)
加法: ((x & 0x7f..) + (y & 0x7f..)) ^ ((x ^ y) & 0x80..)
```

回归用例 `test_swar_subtract_matches_per_byte_loop` / `test_swar_add_matches_per_byte_loop`
拿朴素逐字节实现做对照，`test_extreme_values_do_not_leak_between_lanes` 专挑
`255-0`、`0-255`、`128±127` 这些边界值，专门抓串道。

**坑四：测试写错了，工具是对的。**
`test_average_filter_uses_floor_of_mean` 一开始期望第一个像素输出 0，实际是 1。
我算错了：第一像素的「左」是 0，「上」是 1，均值 `(0+1)//2 = 0`，所以原值 1 减 0 还是 1。
测试先红后绿，错的是测试。

**坑五：memLevel 9 并不更好。**
zlib 的 `memLevel` 从默认 8 提到 9，理论上哈希表更大、匹配更多。
实测一半文件更小、一半更大：`card1.png` 是 421,088 → 423,537 B（变差了 0.6%），
`banner.png` 反过来小一点。净收益约等于 0，于是退回默认值，顺手把这条注释写进代码里。

**坑六：paeth 慢 30 倍，只能当整图候选。**
逐行自适应本来想在五种滤波里选，但 paeth 需要每字节三次比较，实测 1.5 MB/s，
而 SWAR 那几个是 50-100 MB/s。于是逐行自适应只用 none/sub/up/avg 四种，
paeth 保留为「整图统一用 paeth」这一个候选。实测在三个文件上对比：
自适应含 paeth 与不含 paeth 互有胜负，差距 0.7-1.5%，不值得为它让每次滤波慢 30 倍。

**坑七：三个 `.png` 其实是 JPEG。**
语料里 3 个文件签名是 `FF D8 FF E0`（JFIF）。最初的错误信息是「not a PNG file」，
用户会以为是工具坏了。改成直接说出来：
`if the name ends in .png but the contents are a JPEG or WebP, rename it or convert it first`。
回归用例 `test_not_a_png` 断言这句话在错误信息里。

## 八、一句话总结

oxipng 花了 38 个参数和 6 个 reduction 模块去换最后 0.36%，
而它真正值钱的那 7.3% 全部藏在一个我们调不动的 C 库里——
这件事本身比压缩率有意思：**工具的上限常常不在算法，而在你被允许链接哪个压缩器。**
