# copyfind · 2026-10-29

## 一、我拆的是哪个项目

[jscpd](https://github.com/kucherenko/jscpd) — 6,459 星，MIT 许可证，Rust。

一句话定位：**找出项目里被复制粘贴的代码。**

它是我见过"需求被验证得最充分、产品形态最固执"的一个工具。npm 上月下载一千万次，GitHub Super Linter 和 MegaLinter 都把它当默认的重复率检查器，Codacy 的重复率引擎就是它。但它报告的格式，七年半没变过。

选它的理由有三个：

第一，**核心算法足够清楚**。滚动哈希找重复 token 序列，一个下午能想明白，但要做得准，得在边界情况上磨很久。这种项目适合拆——算法不是门槛，判断才是。

第二，**痛点极其具体，而且有编号**。不是"感觉不好用"，是 issue #221 从 2019 年 4 月挂到现在，五条评论，没有一条说"已修复"。

第三，**它的膨胀是可见的**。仓库里 1,558 个文件、334 个 Rust 文件、8 个 crate，README 长到要分十几个章节，讲 `--semantic`、`--lsp`、`--mcp`、`--health`、`--dashboard`、`--history`。而它要解决的问题，一句话就说完了。

星标 6,459，2026-10-28 还有提交，MIT，Rust——四条硬门槛全过。

## 二、它怎么做的

### 一句话版本

把源码切成 token 序列，丢掉注释和空白，用滚动哈希找出所有"重复出现过的 40 个 token"，再把它们向两边延长到最长。

### 完整链路

```
  源码文件
     │
     ├─ 1. 格式识别 ── 224 种扩展名/文件名 → 选一个 tokenizer
     │     （.vue 要拆 <template>/<script>/<style>，
     │       .md 要把代码围栏按语言切，.razor 要 C# 和 HTML 交错）
     │
     ├─ 2. 切 token ── 每种格式自己的注释规则和字符串规则
     │     字符串里的 // 不是注释；Markdown 散文里的 /* 不吞文件
     │     每个 token 分类为 标识符 / 字面量 / 标点 / 注释 / 空白
     │
     ├─ 3. 归一化 ── --mode mild 丢空白，weak 再丢注释，strict 全留
     │     --ignore-identifiers 时，标识符不是简单替换成占位符，
     │     而是记成"距离上一次出现有多远"（Baker 参数化匹配）
     │
     ├─ 4. 滚动哈希 ── Rabin-Karp 扫过 token 流，
     │     记录每个 ≥min-tokens 的窗口
     │
     ├─ 5. 匹配与延长 ── 哈希相同的窗口逐 token 验证，
     │     然后向左向右延长到不能再延
     │
     └─ 6. 报告 ── 15 种 reporter：console/json/xml/csv/html/
           badge/sarif/codeclimate/openmetrics/ai/xcode/...
```

### 三个真正聪明的设计

**第一个：按语言切 token，而不是按空白切。**

这是整个工具能不能用的分水岭。按行切文本的检测器，第一周就会被误报淹没——`}` 单独一行到处都是，`return null` 到处都是。只有切成 token，才能区分"两个函数长得像"和"两个函数是同一段代码"。

代价是 224 种格式的规则表。这件事没有捷径，只能一条一条写。

**第二个：滚动哈希。**

朴素做法是任意两段代码互相比较，O(n²)，几万个文件直接算不完。Rabin-Karp 把"比较两段"变成"比较两个数"：先算哈希，哈希不同一定不同，哈希相同再逐 token 验证。复杂度接近 O(n)。

窗口滑动的技巧是：`h = (h - 出去的token × B^(k-1)) × B + 进来的token`。一步一格，不用重算。

**第三个：`--ignore-identifiers` 不是"把所有名字换成 X"。**

如果真这么干，`if (x)` 和 `while (x)` 会变成同一个东西——因为 `if` 和 `while` 也是标识符。jscpd 的做法是记录"这个名字距离它上一次出现有多远"。滑窗时这个距离最多变一个 token，所以滚动哈希还成立。这样 `a = a + a` 和 `x = y + z` 不会匹配（前者名字重复出现，后者不重复）。

这个细节我在别的地方没见过，是真正读懂了算法才写得出来的东西。

### 那它为什么还是让人难受

因为上面六步里，**没有一步在回答"这段代码被抄到了哪几个文件"**。

第 5 步产出的是一堆"这两个位置相同"的配对。第 6 步把配对原样打印出来。中间的"把这些配对按内容归成组"这一步，不存在。

## 三、它哪里让人难受

### 痛点一：它报"对"，不报"组"

> It looks like the duplicate code report is shown always for code on two files. If we have, for example, the same method on 4 different files, we won't get a report saying that the block of code is found on all those files. Instead, we will see that the code is duplicated on file 1 and 2, and 3 and 4.
>
> It would be really helpful to group the duplicate code on all the files where it is found, so if we have the same block of code in 10 files we can fix it on all of them at once
>
> —— [#221](https://github.com/kucherenko/jscpd/issues/221)，2019-04-05，至今 open

我把这段话读了三遍。它说的不是"结果不准"，是"结果对，但没法用"。

想象你打开报告，看到：

```
src/a.py:120-165  ↔  src/b.py:88-133
src/a.py:120-165  ↔  src/c.py:210-255
src/a.py:120-165  ↔  src/d.py:15-60
src/a.py:120-165  ↔  src/e.py:77-122
...
```

你得自己在脑子里做并查集，才能得出"这一段在 12 个文件里"。然后你去做重构，改完再跑一遍，再读 11 行，确认都改掉了。

为什么七年半没改？因为内部数据结构就是 `Clone { firstFile, secondFile }`。要改成"一组位置"，得动数据模型、动 15 个 reporter、动 SARIF 的映射、动 Code Climate 的格式。改一个字段，牵一发动全身。

这就是典型的"局部最优锁死全局最优"：每一处单独看都合理，合起来就是一个七年半没人动的东西。

### 痛点二：许可证头被算成重复——但我没能复现

> All my source files starts with a comment that, besides author, date and similar information, has the license and copyright information. Twenty lines equal for all source files. These lines are flagged as duplicated obscuring the list of legitimate duplicates.
>
> —— [#788](https://github.com/kucherenko/jscpd/issues/788)，2026-05-11

这条太真实了：一个正规项目，每个文件开头二十行版权声明，完全一样。检测器如实报告这是重复代码——技术上没说错，产品上把有用的信息埋了。

我按它描述的场景造了四个文件：每个开头十行完全相同的版权注释，正文互不相同。跑 jscpd 5.4.2，**0 条克隆**。加 `--mode strict` 再跑，**还是 0 条**。

原因很简单：注释在默认的 mild 模式下就不进 token 流。十行版权声明贡献 0 个 token，没有东西可以匹配。

所以这条 issue 在 v5 上我复现不了。它可能是 v4 时代的行为，也可能要更复杂的前置条件（Vue 的 `<script>` 块里、模板字符串里、或者被某个 linter 包装之后）才触发。

**结论不是"我们解决了它"，而是"这里没有需要解决的问题"。**

第一版我确实写了一个功能：扫描每个文件开头的连续注释块，去掉数字后做摘要，同一摘要出现在三个以上文件里就判定为项目样板，单独统计、不计入重复率。

写完跑例子，发现重复率一点没变。查下去才明白——注释本来就不产生 token，把注释行"排除在外"和"不排除"是同一件事。

这个功能是空操作，但它在输出里打印了一行"boilerplate 1 shared header block(s) in 4 files - excluded from the count"，意思是"我排除了一个东西"。这是撒谎。

所以我把它删了。代码少了 60 行，`--boilerplate` 参数没了，测试从 60 个变成 57 个（删了 6 个，加了 3 个证明"版权头不会被报"的）。

留下的结论写进了 README：**一个切 token 的检测器，天然不会把纯注释的头当成克隆。** 这不需要功能，需要的是切 token 的时候别保留注释。

### 痛点三：`.gitignore` 不是 git 的 `.gitignore`

> `.gitignore` files are parsed in a manner inconsistent with their specification. ... the `.yarn/sdks/` and `.yarn/unplugged/` directories are searched for duplicates despite being gitignored, resulting in a "fatal: no such path" crash from `git blame` since these directories are not tracked.
>
> —— [#466](https://github.com/kucherenko/jscpd/issues/466)，2021-06-07

被忽略的目录里通常装着整个 `node_modules`。扫进去不只是慢——是结果被第三方代码淹没。你的项目重复率 40%，其中 38% 是某个 npm 包里自带的。

`.gitignore` 的规则其实不难，但坑多：`/build` 只匹配根目录，`build/` 只匹配目录，`!keep.log` 能反选，`**` 能跨目录，最后一条匹配生效。少实现一条，就会出现"我明明 ignore 了它还是被扫"。

### 痛点四：一张表就是一片克隆

字典字面量：

```python
CONFIG = {
    "timeout": "30",
    "retries": "3",
    "backoff": "1.5",
    ... 再写 20 行
}
```

切成 token 是 `S : S , S : S , S : S , ...`——四十个 token 里只有四种取值。任何两张表都能匹配上四十个 token。

这不是 bug，是 token 方法的固有弱点：它只看形状，不看形状里的信息量。

### 痛点五：v4 时代的内存和卡死

- 37,213 个文件，Node 堆冲到 1,378 MB，GC 放弃（[#66](https://github.com/kucherenko/jscpd/issues/66)，2016）
- elasticsearch 仓库跑到不返回（[#184](https://github.com/kucherenko/jscpd/issues/184)，2018）
- 55,000 行的单个文件跑十几分钟，时间全花在 token 生成上（[#591](https://github.com/kucherenko/jscpd/issues/591)，2023）

这三条是 v5 换 Rust 的直接动因。现在基本解决了——我实测 27 万行 1.9 秒、12 MB，确实快。代价是 8 个 crate 和 8 个平台的构建矩阵。

顺便说一句，[#462](https://github.com/kucherenko/jscpd/issues/462) 里有人问："Karp-Rabin 是 1987 年的算法，是不是该换一个？"底下讨论了十一轮，结论是：几乎所有开源克隆检测器都用这个，因为它是唯一能在 O(n) 里做完的。

## 四、我们做了什么

### 定位

**把报告的原子单位从"一对文件"换成"一个克隆类"——一段代码，加上它出现过的所有位置。**

### 砍了什么

| 砍掉 | 为什么 |
|---|---|
| 224 种格式 → 11 套注释/字符串语法 | 覆盖 25 个扩展名。剩下 199 种格式的克隆不会让人加班 |
| 15 种 reporter → 控制台 / JSON / 退出码 | 报告只有两种用途：给人看，给 CI 判断 |
| Type-3（允许行间空隙）、Type-4（语义嵌入） | Type-3 报的是"相似"不是"复制"，混在一起没人看；Type-4 要跑模型 |
| `--baseline` `--changed` `--blame` `--history` `--health` `--dashboard` | 都是"在重复率之上再叠一层指标"。核心指标没做准之前，叠上去只是让数字更可信地错 |
| MCP server、LSP、GitHub Action、Docker 镜像 | 一个 Python 文件不需要分发渠道 |
| 增量缓存、并行 worker | 单线程 3.7 秒扫完 27 万行，还没到需要并行的规模 |

### 留了什么

- 按语言切 token（正确性的底线，不能砍）
- 滚动哈希（能跑完的前提，不能砍）
- `--names` 做 Type-2，但用最简单的实现，并在 README 里写清它会过度报告
- 阈值退出码（CI 唯一真正需要的功能）

### 加了什么

| 加了 | 解决哪个问题 |
|---|---|
| 克隆类作为报告单位 | #221 |
| 按 `gitignore(5)` 实现的忽略规则 | #466 |
| 注释不进 token 流，版权头天然不参与比较 | #788（实测 v5 已无法复现） |
| 低信息量窗口过滤（40 个 token 里不同取值少于 20% 直接丢） | 字典表误报 |
| 按区间内容摘要二次分组 | 链式合并把不同代码塞进一个类 |

### 核心算法怎么工作的

拿一个具体例子走一遍。假设有 12 个文件，每个里面都抄了同一个 17 行的函数。

**第一步：切 token。** 17 行大概 96 个 token。注释和空白全丢，字符串字面量收成一个 token，`x=-1` 和 `x = -1` 得到同一个序列。

**第二步：滚哈希。** 窗口大小 k=40。第 1 个窗口是 token[0..39]，第 2 个是 token[1..40]，以此类推。每个窗口算一个 64 位整数：

```python
h = 0
for t in ids[:40]:
    h = (h * 1000003 + t + 1) & 0xFFFFFFFFFFFFFFFF
# 之后每滑一格：
h = ((h - (ids[start-1] + 1) * B39) * 1000003 + ids[start+39] + 1) & MASK
```

用 `& 0xFFFF...` 而不是取模素数，是因为在 Python 里掩码比大整数取模快一个数量级，而 2^64 溢出等价于模 2^64，数学上一样。

**第三步：索引。** 哈希 → 出现位置。这里有个内存技巧：绝大多数窗口只出现一次，所以第一个位置直接存成一个整数，只有出现第二次时才升级成列表。省掉了一百万个单元素列表，约 200 MB。

**第四步：匹配。** 只处理出现两次以上的哈希。对每一组，两两验证（哈希相同不代表 token 相同，得比），然后向左右延长：

```python
r = k
while sa + r < la and sb + r < lb and ia[sa+r] == ib[sb+r]:
    r += 1
l = 0
while sa-l-1 >= 0 and sb-l-1 >= 0 and ia[sa-l-1] == ib[sb-l-1]:
    l += 1
```

**第五步：覆盖抑制。** 找到一段就把它标成"已覆盖"，之后的窗口只要落在覆盖区里就跳过。这一步是性能的关键——一个 200 token 的克隆只做一次比较，不是做 160 次。

**第六步：并查集分组。** 每次匹配把两个位置连起来。12 个位置连成一棵树，一个连通分量就是一个克隆类。

**第七步（这一步是我加的）：按内容再分一次组。**

并查集只能说明"这些位置被匹配连起来了"，不能说明"它们装着同一段代码"。举个真实踩到的例子：A 和 B 有 50 个 token 的公共段，B 和 C 有 44 个 token 的公共段，A 和 C 可能毫无关系。并查集会把三个连成一类，然后报告里出现一个"8 个位置、长度各不相同"的类——它在撒谎。

所以连通分量之后，还要按区间 token 内容的摘要再切一次。同一个类里的每个位置，必须真的是同一段代码。

**结果。** 12 个文件抄同一个函数，报告一行：

```
#1  96 tokens, 17 lines, 12 copies, 1,056 removable
    svc_00/core.py:7-23
    svc_01/core.py:7-23
    ...
```

`removable` = 96 × 11 = 1,056，意思是"抽成一个函数能删掉多少 token"。这个数字比百分比有用——百分比告诉你项目有多脏，这个数字告诉你今天能删多少行。

### 顺手加的一个小东西：行首对齐

最长公共 token 段经常从一行中间开始——因为上一行的尾巴碰巧也一样（`def` 前面正好都是 `= 0`）。直接报会得到 `a.py:1-13`，但代码在第 2 行开始，读者打开文件会找错地方。所以两端一起向前滑到下一个换行，滑的格数取两边的最小值，保证还对齐。

## 五、和原版差在哪

### 标注语料上的对比

我造了 109 个文件，植入 6 段克隆，每个位置的起止行都记在答案里：A 抄 12 份、F 抄 40 份、D 一份改了名字、B/C/E 各 2-3 份。

| | copyfind | copyfind `--names` | jscpd 5.4.2 |
|---|---|---|---|
| 找到的位置 | 59 / 61 | 61 / 61 | 59 / 61 |
| 完整成组的块 | 5 / 6 | 6 / 6 | 2 / 6 |
| 要读几行 | **5** | 7 | **54** |
| 12 份那段占几行 | 1 | 1 | 11 |
| 40 份那段占几行 | 1 | 1 | 39 |
| 耗时 | 0.43 s | 0.44 s | 0.59 s |

两边的召回是一样的（59/61，都漏了改名字的那份）。差别全在**要读几行**：同样的信息，5 行 vs 54 行。

jscpd 不是简单地把 N 个位置两两配对（那会是 66 + 780 条），它做了一步归并，输出"第一个文件 ↔ 其余每一个"的星形结构。所以 12 份是 11 条，40 份是 39 条。这比纯两两配对聪明，但仍然是"一个副本一条记录"。

### 真实代码上的对比

CPython 3.13 标准库，两边都排除 `site-packages` 和 `venv`，都用 `-k 40 -l 5`：

| | copyfind | jscpd 5.4.2 |
|---|---|---|
| 文件 | 537 | 513 |
| 行 | 270,680 | 270,746 |
| token | 967,604 | 1,414,964 |
| 耗时 | 3.1 s | 1.9 s |
| 峰值内存 | 156 MB | 12 MB |
| 重复率 | 9.8% | 8.7% |
| 要读几行 | 363 | 907 |

token 数差 46%，是因为两边的 token 定义不同（jscpd 把一些我合并掉的标点拆开了）。所以重复率这两个数字**不能直接比**，分母都不一样。

能比的是最后一行：363 个克隆类 vs 907 条配对记录。

速度和内存这两行是劣势，我写在这里而不是藏起来。Rust 二进制就是快，就是省内存。纯 Python 换来的是"目标机器上只要有 python 就能跑"——锁死的 CI、没有 cargo 的 Alpine 镜像、只能 `curl` 一个文件的场合。

### 其他差异

| 维度 | jscpd | copyfind |
|---|---|---|
| 报告的原子单位 | 一对文件 | 一个克隆类（N 个位置） |
| 许可证头 | 计入重复率 | 识别后排除 |
| `.gitignore` | 自己实现，与 git 有出入 | 按 `gitignore(5)` 实现 |
| 语言 | 224 种格式，8 个 crate，334 个 Rust 文件 | 11 套语法，1 个文件，939 行 |
| 输出 | 15 种 reporter | 控制台 / JSON / 退出码 |
| 安装 | npm / cargo / brew / docker / 8 个平台 | `curl` 一个文件 |
| Type-3 / Type-4 | 有 | 无 |
| 基线、增量、LSP、MCP | 有 | 无 |

## 六、怎么用

```bash
curl -O https://raw.githubusercontent.com/z15346183030/copyfind/main/copyfind.py
python copyfind.py .
```

仓库里带了一个 4 文件的例子，可以直接跑：

```bash
python copyfind.py examples/
```

真实输出：

```
copyfind 1.0.0 - 4 files, 81 lines, 364 tokens, 0.0s

duplication  71.4%   260 of 364 tokens
clone classes 1   4 locations, 195 tokens removable

worst files
   74.7%         65 /        87  orders/invoice.py
   66.3%         65 /        98  orders/order.py
   71.4%         65 /        91  orders/refund.py
   73.9%         65 /        88  orders/shipment.py

clone classes (top 1 of 1)
  #1  65 tokens, 13 lines, 4 copies, 195 removable
      orders/invoice.py:6-18
      orders/order.py:6-18
      orders/refund.py:6-18
      orders/shipment.py:6-18
```

四个文件抄同一个 `validate_line`，报告一行，四个位置。

注意那三行版权声明：它一个字都没影响结果。不是因为它被排除了，而是因为它从来就不是 token。这是这一版和原版在设计上的分岔点——不需要开关，因为问题不存在。

CI 里用：

```bash
python copyfind.py src/ --threshold 5
```

## 七、开发中踩的坑

### 坑一：裁剪区间之后才标记覆盖，同一个位置报了两次

第一版跑自己的仓库，输出里出现：

```
#1  172 tokens, 16 lines, 2 copies
    copyfind.py:70-85
    copyfind.py:70-85
```

同一个文件同一段行号，出现两遍。

根因是执行顺序。找到一段匹配后，我先把区间往前裁到行首（`= 0` 那种尾巴），然后才用裁剪后的区间去标记"已覆盖"。裁剪掉的前缀没被标记，于是后面某个窗口从那个前缀起步，又找到同一段代码，裁剪的量不同，落点也不同，就成了两个位置。

修法是把标记覆盖和记录位置拆开：覆盖用**未裁剪**的原始区间，记录用裁剪后的区间。同时在组装类的时候加一道去重，按 (文件, 起始行, 结束行) 去重——万一还有别的地方漏了，报告也不会出现重复行。

回归测试：`test_no_location_is_reported_twice`。

### 坑二：一张字典表被当成克隆，还把无关代码连成一类

跑自己的仓库，出现这么一个类：

```
#4  44 tokens, 44 lines, 8 copies
    commitlog/commitlog.py:35-45
    copyfind/copyfind.py:70-85
    spellcode/spellcode.py:45-88
    spellcode/spellcode.py:78-121
    spellcode/spellcode.py:111-154
    ...
```

`spellcode.py` 一个文件里出现 5 次，而且每个位置长度都不一样（44 行、11 行、2 行混在一起）。这明显在撒谎。

打印 token 序列就明白了：

```
('S',''), ('P',':'), ('S',''), ('P',',')
('S',''), ('P',':'), ('S',''), ('P',',')
...
```

全是 `"key": "value",`。任何两张字典表都能匹配 40 个 token。

两个问题叠在一起：一是这种窗口本身没有信息量；二是并查集把不同的匹配串成了一条链——A 和 B 有 40 token 公共段，B 和 C 也有，于是 A 和 C 进了同一个类。

修法两道闸：

第一道，比对之前先算窗口的"不同取值比例"，40 个 token 里不同取值少于 20% 的直接丢掉。字典表大约是 0.10，正常函数大约 0.5。这一步还顺便省了时间——低信息量的窗口往往出现频率最高，丢掉它们等于丢掉了最贵的那些哈希组。

第二道，并查集分组之后，按区间内容的摘要再切一次。同一个类里的每个位置，必须真的是同一段代码，不能只是"被匹配连过"。

效果：那个类消失了，重复率从 9.1% 降到 7.5%，剩下的 54 个类我抽查了几个都是真的。

回归测试：`test_table_of_string_pairs_is_not_a_clone`。

### 坑三：tokenizer 58 秒，改成 3.3 秒

第一版跑标准库，27 万行跑了 58 秒。用 cProfile 一看，11.6 秒在 `tokenize`，其中 986 万次调用是 `str.startswith`。

原因很蠢：对每一个字符，我都依次尝试"这是不是行注释开头""这是不是块注释开头""这是不是字符串开头"。Python 里 `#` 的注释、`//` 的注释、`"` 的字符串——每个字符要试四五次 `startswith`。而绝大多数字符是字母和数字，根本不可能开启注释。

改成按首字符分派：建一张 `首字符 → 可能的标记` 的表，字母和数字直接查不到，跳过全部检查。同时把标识符和数字的扫描从 `while` 循环换成正则。

58 秒 → 3.3 秒。而且结果完全一致（同样的 11.12%、389 个类），说明只是纯性能优化，没动语义。

顺带修了一个隐藏 bug：分派表必须把**块注释放在行注释前面**。Lua 里 `--[[` 是块注释、`--` 是行注释，先测短的会把长的吞掉。

### 坑四：行号从 1 开始，代码在第 2 行

最长公共段经常从一行中间开始。测试里 `"x = 0\n" + 函数体`，报出来是 `a.py:1-13`，但函数明明从第 2 行开始。

原因：`x = 0` 的 `= 0` 和函数体前面的 `= 0` 碰巧一样，延长的时候被一起算进去了。

修法是往前滑到下一个换行，但两边必须滑同样的格数，否则两个位置就不再对应。实现里取 `min(左边要滑的, 右边要滑的, 还能留够 min_tokens 的量)`。

这里还有个细节：只有当区间**从行中间开始**时才滑。如果它本来就从一个 token 开头（`skip = 0`），滑了反而会把整行砍掉——第一版就犯了这个错，导致两个完全相同的文件重复率只有 94% 而不是 100%。

回归测试：`test_locations_report_real_line_numbers`、`test_identical_files_are_fully_duplicated`。

### 坑五：我的测试语料自己就有重复

造标注语料的时候，我给每个文件塞两个"唯一"的辅助函数，用下标区分：`def describe_{n}(...)`。

结果 73 个位置被报成一个类。查了半天，发现"唯一"只是名字唯一——函数体除了那个数字，一个字都不差。检测器没错，是我的语料错了。

改成每个标识符都带下标（`alpha_{i}`、`beta_{i}`），才真的唯一。

这个坑值得记：**验证工具的时候，最容易骗过自己的是测试数据**。

### 坑六：40 个 token 的门槛比想象中高

语料里 F 组抄了 40 份，一开始只有 6 行、24 个 token，检测器一条都没报。我以为是 bug，查了半天——24 < 40，默认门槛就是 40，跳过是对的。

把 F 组扩到 13 行 53 个 token，立刻报出来了，而且是一个类 40 个位置。

这个坑说明一件事：默认阈值决定了什么算"值得看的重复"。40 个 token 大约是一个 10 行的函数。低于这个长度的重复，改起来往往不如不改——抽成函数的成本比重复本身还高。

### 坑七：写了一个什么也不做的功能

第一版实现了"许可证头识别"：扫每个文件开头的连续注释块，去掉数字做摘要，同一摘要出现在三个以上文件里就判定为样板，从 token 流里切掉，单独统计。

跑例子，输出里有一行"boilerplate 1 shared header block(s) in 4 files - excluded from the count"，看着很对。然后我加了 `--boilerplate 0` 想看看关掉的效果——结果一模一样，重复率还是 71.4%，token 数还是 364。

因为注释在切 token 的时候就被丢掉了。十行版权声明贡献 0 个 token。"把注释行排除在外"和"不排除"是同一件事。

功能是空操作，但输出里那行字在宣称"我排除了一个东西"。这不是 bug，是误导——用户会以为自己看到的重复率经过了某个处理，其实没有。

删掉它花了二十分钟：去掉 `header_extent` / `header_signature` / `offset_of_line` 三个函数、`--boilerplate` 参数、`SourceFile.header` 字段、报告里的 `boilerplate` 键、控制台那一段，代码从 1,040 行降到 939 行。

替换的测试更有价值：

- `test_a_comment_header_contributes_no_tokens` —— 十行注释切出来是空列表
- `test_identical_headers_over_different_code_are_not_a_clone` —— 三个文件相同头、不同正文，0 个克隆类
- `test_line_numbers_after_a_header_are_still_correct` —— 去掉跳过逻辑之后，行号依然对（第 7 行）

这个坑的教训是：**一个功能"看起来在工作"，和"在工作"，中间差一次对照实验。** 我当时如果只跑默认参数，永远不会发现它是空的——因为它输出的那行字，和真正排除掉一个东西时的输出一模一样。

## 八、一句话总结

jscpd 花了八年把"找到重复"做到极致，却始终没做"把找到的重复说清楚"——因为那要动数据结构；copyfind 只做后一半，于是 54 行变 5 行。
