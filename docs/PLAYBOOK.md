# 选题与实现规范

这份文档是每日任务的执行标准。任何一天的项目都必须满足这里的全部要求。

**核心结构：一个工具 = 一个独立仓库。** 不是在一个大仓库里开子目录。

---

## 一、选题标准

### 硬性门槛（不满足直接淘汰）

| 条件 | 要求 | 怎么验证 |
|------|------|----------|
| 星标 | ≥ 1000 | `api.github.com/repos/{owner}/{repo}` 的 `stargazers_count` |
| 活跃度 | 最近 90 天内有提交 | `pushed_at` 字段 |
| 许可证 | MIT / Apache-2.0 / BSD / ISC / MPL-2.0 | `license.spdx_id` |
| 语言 | 与我们的实现栈兼容（Python / TypeScript / Go / Rust） | `language` 字段 |
| 可精简 | 存在明确的「功能臃肿」痛点 | issue 里有人抱怨复杂度/配置多/太重 |

**明确排除：**

- GPL / AGPL / SSPL 项目——可以读思路，但绝不复用代码
- 纯 UI 组件库、纯 Awesome 列表、教程仓库、模型权重仓库
- 已经极度精简的项目（没有优化空间）
- 需要私有数据、付费 API、特定硬件才能跑的项目
- 已做过的灵感来源项目（同一个上游不重复拆）

### 加分项（同等条件下优先）

- issue 里有大量「too complex」「hard to configure」「why do I need X」类反馈
- 项目已经很长时间没有大版本更新，但需求仍然旺盛
- 核心功能可以抽象成一个单一职责的小工具

## 二、拆解流程

选中项目后，按顺序做四件事：

### 1. 读 README，写出「它承诺解决什么问题」

一句话。如果一句话说不清，说明这个项目的定位本身就是模糊的——换一个。

### 2. 读目录结构和入口文件，画出核心链路

不要读全部代码。找到 main / cli / index 入口，顺着主流程读，搞清楚：

- 数据从哪进来
- 核心处理逻辑分几步
- 结果从哪出去
- 哪些模块是「核心」，哪些是「周边」（配置系统、插件系统、UI、i18n……）

### 3. 读 issue，找痛点

按 `comments` 排序取前 20 个 open issue，以及近期关闭的 20 个。重点找：

- 复杂度抱怨（配置太多、概念太多、文档看不懂）
- 性能问题
- 常见误用导致的 bug

**这一步的产出直接决定我们的差异化在哪里。** 没有找到痛点，说明这个选题不该做。

### 4. 写出 ANALYSIS.md

固定结构：

```markdown
# 灵感来源：[owner/repo](url)

- 星标：N
- 许可证：SPDX-ID
- 语言：X
- 它承诺解决：一句话

## 它做对了什么
（3-5 条，具体到设计决策）

## 它在哪里让人痛苦
（引用真实 issue，带链接）

## 我们的取舍
（砍掉了什么，为什么；保留了什么，为什么）

## 与原版的差异
（用表格对比，只列真正有差异的维度）

## 许可证说明
（参考项目许可证；如有代码片段复用，标注具体位置和来源）
```

## 三、仓库命名与创建

### 命名规则

仓库名按**工具的用途**取，不是按日期或灵感来源。

- 全小写，用连字符分隔，不超过 20 个字符
- 优先用一个能自解释的单词：`squeeze`、`depmap`、`sift`
- 单词太泛就加限定：`log-sift`、`sql-lint`
- **不要**用 `2026-10-20-xxx`、`daily-tool-12` 这种看不出用途的名字

判断标准：别人只看到仓库名，能不能大致猜到它是干什么的。

### 仓库设置

- 可见性：public
- 初始化：**不要**勾 README / .gitignore / license（本地已经有）
- 描述：一句中文说清用途
- 话题标签：3-6 个，覆盖语言和用途

### 仓库结构

工具文件直接放在仓库根目录，不要再套一层子目录：

```
<repo-name>/
├── README.md          # 必填：是什么 + 怎么用 + 一个示例
├── ANALYSIS.md        # 必填：拆解结论（结构见上）
├── LICENSE            # MIT
├── .gitignore
├── <name>.py          # 源码（简单工具单文件）
└── tests/             # 测试
```

## 四、实现标准

### 必须满足

1. **能独立运行**：单独 clone 下来，装好依赖就能跑，不依赖 daily-forge
2. **零配置启动**：默认参数下能直接跑，配置项越少越好（理想是 0 个必填项）
3. **有测试**：至少覆盖核心逻辑，`python -m unittest discover -s tests` 能一键跑过
4. **有 README**：三分钟内能看懂怎么用，含一个可直接复制粘贴的示例
5. **真实运行验证**：提交前必须实际执行一次，确认输出正确；有量化指标的要实测出数字

### 代码质量

- 核心逻辑与 IO 分离，核心逻辑可纯函数测试
- 错误信息说人话，告诉用户「怎么办」而不只是「哪里错了」
- 不引入不必要的依赖。能用标准库就用标准库
- 单文件优先。除非确实需要，不要拆成十几个模块

## 五、提交前检查清单

- [ ] 星标 ≥ 1000，许可证已确认，不是已做过的上游
- [ ] 仓库名能自解释用途
- [ ] ANALYSIS.md 四段齐全，痛点引用了真实 issue
- [ ] 从干净环境能跑起来，测试全绿
- [ ] README 里的示例命令实际跑过
- [ ] 没有从参考项目复制的代码（或已明确标注）
- [ ] 独立仓库已创建并推送成功
- [ ] daily-forge 的 README 项目列表已加一行
- [ ] commit 作者是 `赵旭 <2210914541@qq.com>`
- [ ] 仓库里没有任何 AI / WorkBuddy / Claude / Codex 字样

## 六、commit message 格式

```
<动词> <工具名>：<一句话说明>

灵感来源 <owner/repo>（N stars，SPDX），未复用其代码。

<核心技术取舍 1-3 句>

实测：<量化数据>
测试：N 个用例全部通过。
```

动词用「初始化」「新增」「重写」这类直白的中文，不用 `feat:` `chore:` 前缀。
