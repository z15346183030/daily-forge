# 设计与实现规范

这份文档是每个工具的交付标准。任何一个仓库都必须满足这里的全部要求。

**核心结构：一个工具 = 一个独立仓库。** 不是在一个大仓库里开子目录。

---

## 一、选题标准

### 硬性门槛（不满足直接淘汰）

| 条件 | 要求 | 怎么验证 |
|------|------|----------|
| 问题 | 一句话能说清输入、输出和边界 | 写不出来的，说明还没想清楚 |
| 频率 | 是真实、重复出现的需求 | 自己或身边人一周内至少遇到一次 |
| 可验证 | 有明确的正确性标准 | 能用测试用例或真实数据证明对错 |
| 可量化 | 效果能测出数字 | 速度、体积、误报率、覆盖率，至少有一项 |
| 体量 | 单文件能写完，依赖接近零 | 标准库优先，超出就砍功能 |

**明确排除：**

- 需要私有数据、付费 API、特定硬件才能跑的想法
- 纯 UI 组件库、纯 Awesome 列表、教程仓库、模型权重仓库
- 已经有工具把这件事做到极致、且没有明确改进空间的方向
- 为了用上某个新技术而造的需求

### 加分项（同等条件下优先）

- 默认行为容易出错、需要反复解释的领域
- 现有流程里靠人工检查、容易漏掉的一步
- 结果需要「可解释」，而不只是「能跑」

## 二、设计流程

确定需求后，按顺序做四件事：

### 1. 写清楚问题

一段话回答：谁在什么场景下遇到什么问题，现在怎么解决，为什么不够好。

### 2. 设计最小接口

- 默认参数下必须能直接用
- 每个配置项都要能回答「不加会怎样」
- 一个命令只做一件事，子命令之间不共享隐式状态

### 3. 定义「正确」

在写实现之前先写验证方式：

- 哪些输入必须得到什么输出
- 哪些边界情况必须不崩
- 用哪份真实数据、量哪个指标

没有验证方式的功能不做。

### 4. 写实现与测试

- 核心逻辑与 IO 分离，核心逻辑可纯函数测试
- 错误信息说人话，告诉用户「怎么办」而不只是「哪里错了」
- 测试至少覆盖核心逻辑和已知边界

---

## 三、仓库命名与创建

### 命名规则

仓库名按**工具的用途**取。

- 全小写，用连字符分隔，不超过 20 个字符
- 优先用一个能自解释的单词：`squeeze`、`depmap`
- 单词太泛就加限定：`log-sift`、`sql-lint`
- **不要**用 `2026-10-20-xxx`、`daily-tool-12` 这种看不出用途的名字

判断标准：别人只看到仓库名，能不能大致猜到它是干什么的。

### 仓库设置

- 可见性：public
- 初始化：**不要**勾 README / .gitignore / license（本地已经有）
- 描述：一句中文说清用途
- 话题标签：3-6 个，覆盖语言和用途

### 仓库结构

工具文件直接放在仓库根目录，不要再套一层子目录：

```
<repo-name>/
├── README.md          # 必填：是什么 + 怎么用 + 设计取舍
├── LICENSE            # MIT
├── .gitignore
├── <name>.py          # 源码（简单工具单文件）
├── examples/          # 可选：可直接运行的示例
└── tests/             # 测试
```

## 四、实现标准

### 必须满足

1. **能独立运行**：单独 clone 下来，装好依赖就能跑，不依赖 daily-forge
2. **零配置启动**：默认参数下能直接跑，配置项越少越好（理想是 0 个必填项）
3. **有测试**：至少覆盖核心逻辑，`python -m unittest discover -s tests` 能一键跑过
4. **有 README**：三分钟内能看懂怎么用，含一个可直接复制粘贴的示例
5. **真实运行验证**：提交前必须实际执行一次，确认输出正确；有量化指标的要实测出数字

### 代码质量

- 核心逻辑与 IO 分离，核心逻辑可纯函数测试
- 错误信息说人话，告诉用户「怎么办」而不只是「哪里错了」
- 不引入不必要的依赖。能用标准库就用标准库
- 单文件优先。除非确实需要，不要拆成十几个模块

## 六、commit message 格式

```
<动词> <工具名>：<一句话说明>

<核心技术取舍 1-3 句>

实测：<量化数据>
测试：N 个用例全部通过。
```

动词用「初始化」「新增」「重写」这类直白的中文，不用 `feat:` `chore:` 前缀。
