# Daily Forge

每天从 GitHub 上挑一个千星以上的项目，拆解它的设计，然后**用我们自己的代码**做一个更小、更聚焦、更好用的版本。

不是 fork，不是搬运，不是换个皮。是看完别人怎么解决问题之后，自己动手写一遍。

---

## 为什么做这个

GitHub 上有大量优秀的工具，但它们往往解决的是「所有人的问题」——所以功能臃肿、配置复杂、上手门槛高。

Daily Forge 的逻辑很简单：

1. **找一个被验证过的需求**（千星就是最好的需求验证）
2. **读它的代码和 issue**，搞清楚它做对了什么、又在哪里让人痛苦
3. **砍掉 80% 的功能，只保留最核心的那 20%**，然后把它做到极致简单
4. **用我们自己的实现写出来**，推到这里

每天一个，日拱一卒。

## 目录

每个工具一个独立目录，自包含、可单独运行：

```
tools/
└── YYYY-MM-DD-slug/
    ├── README.md       # 这个工具是什么、怎么用
    ├── ANALYSIS.md     # 灵感来源、拆解结论、我们改了什么
    ├── src/            # 源代码
    └── tests/          # 测试
```

## 三条硬规矩

**1. 只学思路，不抄代码。**

拆解阶段会读参考项目的源码，目的是理解它的架构决策和取舍。但落到 `src/` 里的每一行，都是我们自己写的。

如果参考项目是 MIT / Apache-2.0 / BSD，允许在保留版权声明的前提下复用代码片段——但我们仍然优先自己实现，实在需要复用时会在 `ANALYSIS.md` 里明确标注来源和许可证。

**GPL / AGPL 项目的代码一行都不会进这个仓库。** 这类项目只看思路，实现完全独立完成。

**2. 每个工具必须能跑。**

没有「规划中」「即将支持」。进了 `tools/` 的，就是装好依赖、跑起来、有测试的。

**3. 每个工具必须比原版更简单。**

如果一个工具做完之后，配置项比原版还多、上手比原版还慢，那这个工具就不该存在。简单是唯一的产品指标。

本仓库代码采用 MIT 许可证，详见 [LICENSE](LICENSE)。

各工具目录下的 `ANALYSIS.md` 会记录其灵感来源项目的许可证信息。参考项目的许可证不影响本仓库自有代码的授权，但复用的代码片段会单独标注。

## 关于「每天一个」的诚实说明

这不是手写的。

每天定时任务会：抓 GitHub Trending → 按「千星以上 + 许可证干净 + 能在一天内做出有价值的精简版」筛出候选 → 拆解架构和 issue → 写一个自包含的最小实现 → 跑通测试 → 提交。

筛选和初稿由 AI 完成，但每个工具都经过真实运行验证——跑不起来的不会进仓库。
